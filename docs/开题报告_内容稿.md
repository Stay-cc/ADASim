# 面向自动驾驶算法的轻量级高帧率仿真平台 ADASim 设计与实现

## 一、课题背景与研究意义

### 1.1 研究背景

自动驾驶系统由感知、预测、规划、控制四个环节串联构成，其安全性与可靠性高度依赖大里程的道路验证。业界普遍估计，要使自动驾驶系统的安全性达到人类驾驶员的水平，需要累积数亿乃至数十亿公里的测试里程。然而，实车路测面临三重现实约束。

其一，成本高昂。测试车辆、安全员、测试场地与能耗成本叠加，单个有效测试小时的边际成本远高于软件测试，难以支撑算法迭代期的高频验证需求。

其二，长尾场景难以复现。导致交通事故的往往是低概率的极端场景——前车紧急切入（cut-in）、行人突然横穿、施工区临时改道、雨雾导致的传感器退化等。这类场景在自然驾驶数据中出现的频率极低，靠里程累积去"撞见"它们在经济上不可行。

其三，危险场景无法做边界测试。要验证系统的失效边界，必须把车辆置于可能发生碰撞的工况中，这在实车上既不允许也不安全。

因此，基于仿真的测试（Simulation-based Testing）已成为自动驾驶研发流程中不可替代的环节，并形成了模型在环（MIL）、软件在环（SIL）、硬件在环（HIL）、车辆在环（VIL）的分层验证体系。其中 MIL 与 SIL 位于算法迭代的最前端，直接决定一个算法从"想法"到"可被数据验证的原型"需要多长时间。也正因如此，仿真平台自身的启动速度、迭代效率与部署门槛，会以乘数效应影响整个算法研发的产出效率。

### 1.2 现有仿真平台的能力边界

当前主流仿真平台可分为三个层次：面向感知与整车验证的高保真 3D 仿真器、面向交通流与宏观行为的仿真器、以及面向决策与规划算法的轻量级仿真工具。三者的能力分布呈现出明显的取舍关系，具体对比见表 1。

表 1 典型自动驾驶仿真平台能力对比

| 平台 | 渲染维度 | 传感器模型 | 车辆模型 | 开发语言 | 硬件门槛 | 典型定位 |
| --- | --- | --- | --- | --- | --- | --- |
| CARLA | 3D（UE4） | 相机、激光雷达、毫米波、语义分割 | 动力学 | C++ / Python | 独立显卡，显存 4 GB 以上，资产数十 GB | 高保真城市仿真 |
| Apollo + DreamView | 3D | 全套 | 动力学 | C++ / Python | Docker、独立显卡、高精地图 | 实车同源全栈验证 |
| SUMO | 2D 路网 | 无 | 跟驰与换道模型 | C++ / Python | 极低 | 交通流宏观仿真 |
| CommonRoad | 2D | 无 | 运动学 | Python | 低 | 规划算法基准测试 |
| MetaDrive | 3D | 简化 | 运动学 | Python | 中等 | 强化学习场景生成 |
| highway-env | 2D | 无（抽象观测） | 运动学 | Python | 极低 | 决策算法快速验证 |
| ADASim（本课题） | 2D BEV + 点云 | 激光雷达点云 | 运动学自行车模型 | C++ / Qt + Python | 集成显卡即可运行 | 全链路算法快速闭环 |

由表 1 可见，平台设计本质上是在"保真度—迭代效率—硬件成本"三角中做取舍，不存在同时满足三者的通用方案。

### 1.3 问题的提出

结合算法开发者的真实工作流，现有工具链存在六个具体断点。

（1）环境配置成本高。CARLA 需要编译 Unreal Engine 工程或下载预编译包并匹配显卡驱动版本；Apollo 需要 Docker 环境、Cyber RT 中间件与高精地图数据。在实验室公共机房或学生个人笔记本上完整跑通，往往需要数天时间，且极易因驱动或依赖版本不匹配而失败。

（2）硬件门槛苛刻。3D 仿真依赖独立显卡与大显存，在嵌入式开发板、集成显卡笔记本以及后续要部署算法的车规级平台上无法运行，导致"仿真验证环境"与"目标部署环境"严重割裂。

（3）迭代周期长。3D 场景加载与资产解析耗时以秒到分钟计，算法每修改一行代码就要等待场景重新加载，调试的反馈回路被显著拉长。

（4）算法与仿真未真正解耦。多数轻量工具将算法与渲染置于同一 Python 进程内，受全局解释器锁（GIL）与渲染主线程相互拖累；算法的替换、单步调试乃至改用 C++ 实现，都需要改动仿真框架本身。

（5）缺少时间维度的回溯能力。调试时最需要的是"把刚才出问题的那两秒倒回去慢放"，但主流平台多只提供离线录制—回放，不提供运行过程中的任意时刻回溯，导致问题现场难以复现。

（6）场景构建依赖人工经验。新增一个测试场景通常要手工编写配置文件或脚本，场景的覆盖度与危险性取决于编写者的经验；工具链既缺少把"想测的工况"直接转化为可执行场景的便捷通道，也缺少在参数空间中系统搜寻失效边界的机制，测试往往停留在设计者已经想到的几类工况上。

### 1.4 研究意义

理论意义方面，本课题把"算绘分离"这一软件工程原则与"时间可回溯"这一调试需求，落实为可运行的系统架构，并量化验证其在轻量级仿真场景下的性能收益，可为低成本仿真平台的架构设计提供可复用的工程参考。

工程意义方面，平台以 C++/Qt 构建渲染与物理底座、以 Python 承载算法，在不依赖独立显卡的前提下提供高帧率的 2D 鸟瞰（BEV）视图与激光雷达点云渲染，使算法开发者可以在个人电脑或嵌入式设备上完成从感知到控制的全链路闭环验证，显著缩短算法迭代周期。

教学意义方面，平台将感知、预测、规划、控制四个环节的数据流以可视化方式完整呈现，可作为自动驾驶相关课程的实验平台，帮助学生建立对全链路数据流的直观认识。

## 二、国内外研究现状

### 2.1 基于场景的仿真测试与安全评估

自动驾驶仿真研究的一条主线是从"里程驱动"转向"场景驱动"。Riedmaier 等对基于场景的安全评估方法做了系统综述，将评估流程归纳为场景识别、场景生成、场景执行与结果评价四个阶段，并讨论了如何用少量关键场景覆盖高风险工况。国际标准化组织发布的 ISO 34502 给出了基于场景的自动驾驶安全评估框架，对场景的功能、逻辑与具体三个抽象层级做了定义。这一体系的意义在于：仿真的价值不在于"跑得多"，而在于"跑得准"——能否以可复现的方式把系统推向失效边界。这也对本课题提出了架构层面的要求：平台必须能精确控制与回放场景的时间线，否则场景级的量化评估无从谈起。

### 2.2 仿真器平台

Dosovitskiy 等提出的 CARLA 是目前学术引用最广的开源自动驾驶仿真器，基于 Unreal Engine 4 提供城市级 3D 场景、可配置的相机与激光雷达传感器模型以及天气光照条件，并提供 Python API 用于算法接入。CARLA 的优势在于感知层的物理保真度，代价是庞大的资产体量与较高的图形硬件要求。

Apollo 平台以"实车同源"为设计目标，其仿真模块复用实车的 Cyber RT 通信中间件与高精地图，能够最大程度保证仿真行为与实车行为的一致性，但部署依赖 Docker 与完整地图数据，学习曲线陡峭。

商业软件如 PreScan、CarSim、VTD 在传感器物理建模与车辆动力学精度上具备优势，但授权费用高昂，且二次开发受限于厂商提供的接口，难以满足算法研究中频繁调整数据结构的需求。

SUMO 面向交通流仿真，其路网模型与交通需求建模能力突出，但缺少车辆动力学与传感器模型，通常作为场景生成器与其他仿真器联合使用。

在轻量级方向上，CommonRoad 提供了可组合的 2D 道路网络与规划算法基准，Althoff 等将其定位为运动规划算法的可复现评测平台；MetaDrive 通过程序化生成多样化场景支撑强化学习训练；highway-env 以极简的 2D 抽象观测支撑决策算法的快速验证。这类工具的共同优点是依赖少、启动快、易于二次开发，但普遍不提供激光雷达点云等传感器级观测，也难以承载"感知—预测—规划—控制"的完整链路。

### 2.3 支撑技术研究现状

车辆模型方面，Kong 等系统比较了运动学模型与动力学模型在自动驾驶控制设计中的适用性，指出在低速、中小侧向加速度工况下运动学自行车模型已能提供足够精度；Polack 等进一步论证了运动学自行车模型在生成可行轨迹方面的一致性。这为本课题采用运动学自行车模型提供了理论依据。

规划与控制方面，Werling 等提出的 Frenet 坐标系下多项式轨迹采样方法至今仍是横纵向解耦规划的主流方案；Thrun 等提出的 Stanley 横向控制律在 DARPA 无人车挑战赛中得到验证并沿用至今；Borrelli 等对模型预测控制的理论框架与数值实现做了系统阐述。这些工作为本课题算法侧的闭环验证提供了可直接参考的实现路径。

可视化方面，十万级点云的实时绘制需要在绘制调用次数、状态切换开销与数据传输量三方面同时优化，批渲染（Batch Rendering）、空间索引剔除与体素降采样是工程上最常用的三种手段，三者组合使用可将绘制代价从与点数同阶降低到与分档数同阶。

### 2.4 研究现状评述

综合来看，现有工作存在五点不足。

（1）高保真与高迭代效率难以兼得。3D 平台追求传感器与场景的物理保真，代价是资产体量、硬件门槛与启动耗时；轻量平台追求迭代效率，代价是观测抽象化、丢失传感器数据的原始形态。

（2）缺少进程级的算法解耦。多数轻量工具将算法与仿真置于同一进程，算法的编程语言、第三方依赖与调试方式都被仿真框架绑定，难以独立演进。

（3）运行时的时序回溯能力普遍缺失。现有平台多提供离线录制回放，无法在仿真运行中任意回退，而这恰是算法调试中最高频、最刚性的需求。

（4）在低成本硬件上，渲染性能与点云规模之间的矛盾尤为突出。现有轻量 2D 工具几乎不涉及点云渲染，其渲染管线设计无法直接迁移到点云场景。

（5）场景的构建与筛选仍以人工为主。现有平台的场景多由脚本或配置文件手工编写，覆盖度取决于设计者的经验与想象力。近期有工作尝试借助大语言模型降低这一门槛，如 Zhang 等提出的 ChatScene 将自然语言描述转换为仿真器可执行的场景代码，但其依赖特定仿真器的领域语言与代码知识库，迁移到轻量平台需要重新设计中间表示。更重要的是，场景生成与失效筛选大多彼此分离：生成端追求多样，筛选端依赖穷举或随机采样，缺少"先生成候选模板、再在参数空间中定向收敛"的连贯流程。

本课题正是针对上述五点不足，以"算绘分离、时间可回溯、低成本高帧率"为核心，设计并实现一个面向全链路算法闭环的轻量级仿真平台，并在其上补充语言驱动的场景生成与失效搜索能力，使平台从被动的场景执行工具转为主动的场景发现工具。

## 三、研究内容与研究目标

### 3.1 研究目标

设计并实现轻量级自动驾驶算法仿真平台 ADASim。在无独立显卡的嵌入式或个人电脑环境下，实现不低于 60 FPS 的 2D BEV 视图与激光雷达点云渲染（十万点量级），支持仿真运行中任意时刻的时间回溯，通过进程级算绘分离支撑 Python 算法节点的独立开发与替换，最终跑通"感知—预测—规划—控制"全链路闭环，并以量化实验验证平台在帧率、时延、资源占用三方面的表现。在此基础上，平台进一步提供语言驱动的场景生成与参数化失效搜索能力：可由一句自然语言描述构造出参数化场景，并自动在该场景的参数空间中搜索使算法失效的工况组合。

### 3.2 研究内容

（1）仿真底座总体架构与时间管理。设计遵循算绘分离原则的双模块架构：C++/Qt 仿真底座负责物理推演、渲染与通信，Python 算法侧作为独立进程运行。定义固定步长主循环、仿真时钟与真实时钟的解耦机制、实体（自车、障碍物、车道、路口）数据模型与坐标系约定。

（2）滚动窗口回放缓冲（Rolling Window Replay Buffer）。设计环形缓冲结构承载最近若干帧的完整世界状态快照，支持按时间戳或帧号任意定位；研究"完整快照 + 增量重推演"的混合策略，在内存占用可控的前提下保证回溯后的物理状态一致性；实现无限滚动沙盒式的连续场景，避免固定场景的边界效应。

（3）高性能 2D 渲染管线。设计纯内存驱动的绘制管线，研究点云批渲染、按距离与高度分档着色、空间索引剔除、体素降采样的组合优化方案；设计 BEV 视角下的坐标变换与视口管理，支持缩放、跟随与自由视角切换。

（4）车辆运动学与场景建模。实现运动学自行车模型，标定轴距、最大前轮转角、加减速限幅等参数；实现基础场景元素（直道、弯道、多车道、交叉路口）与障碍物行为（匀速、跟驰、切入）。

（5）通信网关与协议设计。基于 Qt 异步网络模块实现 TCP/UDP 双通道：TCP 承载控制指令与结构化状态，保证可靠有序；UDP 承载高频点云数据，优先保证时效。设计带长度前缀的 JSON 报文格式以解决粘包问题，实现心跳检测、超时降级与断线重连机制。

（6）Python 算法节点与全链路闭环。实现独立的算法进程，通过 Socket 与底座进行高频心跳通信；依次实现点云欧氏聚类感知、CTRV 匀速转弯模型预测、Frenet 坐标系采样规划、PID 纵向与 Stanley 横向控制，输出方向盘转角与目标车速，形成闭环。

（7）实验验证与性能评估。设计渲染性能、通信时延、回溯一致性、算法闭环精度、场景生成有效性五组实验，并与 CARLA、highway-env、CommonRoad 等平台在可比维度上进行横向对照。

（8）AI 增强模块。以 JSON Schema 定义参数化场景模板的中间表示，实现自然语言描述到模板的结构化转换、合法性校验与失败回退；定义搜索变量与失效判据，采用贝叶斯优化在参数空间中定向搜索失效工况；模块以插件式独立进程挂载，仅在编辑态与离线批量模式下接入，不占用实时主循环。

## 四、拟解决的关键问题与创新点

### 4.1 拟解决的关键问题

（1）十万级点云在高帧率约束下的绘制效率。逐点绘制会产生与点数同阶的绘制调用开销，在集成显卡环境下直接导致帧率崩塌。解决思路是"减少提交次数、减少提交数据量"：前者用批渲染把 N 次绘制合并为与着色档数同阶的常数次调用，后者用空间索引剔除视口外点、用体素降采样控制参与绘制的点数，目标是单帧绘制耗时不超过 8 ms。

（2）滚动窗口的内存占用与状态一致性。若仅缓存轨迹点，回溯后重新推演会因模型非线性而累积误差；若缓存完整状态，内存随窗口长度线性增长。需要在快照密度与重推演长度之间取平衡，并设计单写多读的访问模式，避免渲染线程与物理线程的竞争。

（3）跨语言通信的时延与同步。JSON 序列化在高频点云传输中开销显著，需在报文体积与解析成本之间权衡；TCP 的 Nagle 算法与粘包问题会引入额外延迟；两个进程的时钟不同步会导致状态错帧。需要设计带序号与时间戳对齐的轻量协议。

（4）低成本硬件上的资源竞争。集成显卡环境下，CPU 同时承担物理推演、点云生成与绘制准备，容易出现帧时间抖动。需要通过任务分级与耗时预算管理，保证物理步进的实时性优先于渲染的流畅性。

### 4.2 创新点

（1）提出并实现"滚动窗口回放缓冲"机制，把仿真世界组织为可无限延伸的环形时间轴，支持运行中的任意时刻回溯与无缝回放，使调试从"复现问题"转变为"倒带观察问题"。

（2）采用进程级算绘分离架构，C++/Qt 底座与 Python 算法节点通过轻量协议解耦，使算法可以独立启动、独立调试、独立替换，同一底座亦可对接不同语言实现的算法。

（3）面向低成本硬件设计了一套组合式 2D 点云渲染优化方案，将批渲染、分档着色、空间剔除与体素降采样协同使用，在无独立显卡条件下达到十万点量级的高帧率绘制。

（4）以"轻量但不残缺"为定位，在 2D 平台上保留传感器级点云观测与全链路闭环能力，弥补现有轻量工具"只有抽象观测"的不足。

（5）将大语言模型与贝叶斯优化组合用于场景构建，形成"语言描述—参数化模板—失效搜索"的链路：前者把场景构建的门槛从编写脚本降到描述工况，后者把有限的仿真预算集中投向最可能失效的参数区域，使平台具备主动发现算法薄弱工况的能力。同时给出 AI 模块的挂载边界约束，保证外部模型的响应时延不侵入实时主循环。

## 五、研究方法与技术路线

### 5.1 研究方法

（1）文献研究法。系统梳理自动驾驶仿真、车辆建模、规划控制三个方向的代表性工作，明确技术选型依据与评价基准。

（2）对比分析法。选取 CARLA、highway-env、CommonRoad 作为对照平台，从冷启动时间、安装体积、最低硬件配置、点云渲染帧率、部署复杂度五个维度做横向比较，界定本平台的能力边界与适用场景。

（3）原型开发与迭代法。采用"最小可运行闭环优先"的策略，先打通"底座渲染一个点、算法算出一个数、通信完成一次往返"的最小链路，再逐步叠加功能，每轮迭代都保持系统可运行、可测量。

（4）实验验证法。以量化指标驱动优化，包括平均帧率、P99 帧时间、端到端时延、跟踪误差均方根等，避免凭主观感受判断性能优劣。

### 5.2 系统总体架构

平台由仿真底座与算法大脑两个主体进程构成，通过本机回环网络通信；此外按需挂载 AI 增强模块作为第三个独立进程。

仿真底座（C++17 / Qt）由四个子系统构成。数据泵以固定步长驱动主循环，每步产出世界状态快照并写入滚动窗口缓冲；物理引擎负责车辆运动学推演与障碍物行为更新；渲染引擎从缓冲读取当前帧状态并绘制；通信网关负责与算法进程交换报文。

算法大脑（Python）为独立进程，包含通信客户端、感知、预测、规划、控制五个模块，以"收到一帧、处理、回发一帧"的节拍运行，与底座通过心跳维持连接。

AI 增强模块同样以 Python 独立进程实现，仅在编辑态（构建场景）与批量离线模式（失效搜索）下接入，通过既有 Socket 通道与底座交换场景配置与仿真结果，不参与实时主循环。三者的进程边界同时也是故障边界：任一进程异常退出，其余两者仍可维持运行或安全停机。

### 5.3 关键技术方案

#### 5.3.1 仿真主循环与时间管理

采用固定步长的物理步进，默认步长 20 ms（50 Hz）。渲染帧率与物理步长解耦：渲染按屏幕刷新率触发，读取最新的物理状态并做时间插值，避免物理步长成为帧率上限。系统维护真实时钟、仿真时钟与逻辑帧号三个时间基准，支持加速、减速与暂停，并保证任意播放速率下物理推演的一致性。

#### 5.3.2 滚动窗口回放缓冲

以环形数组实现，容量为 N 帧，默认取 30 秒 × 50 Hz 即 1500 帧。每帧记录时间戳、自车位姿与运动状态、每个障碍物的位姿与速度、以及算法侧最新输出。写指针随物理步进前移，越界即覆盖最旧帧，从而形成无限滚动的时间轴。

回溯时，读指针定位到目标帧：若该帧为完整快照则直接读取；若为增量帧，则从最近的完整快照出发重推演。系统采用固定间隔快照（每 25 帧一个完整快照）与增量记录混合的策略，在内存与精度之间取平衡。

内存估算：按单帧 200 个障碍物、每障碍物 6 个单精度浮点量估算，单帧约 5 KB，1500 帧窗口约 7.5 MB，在嵌入式设备上亦可接受。

#### 5.3.3 高性能 2D 渲染管线

数据组织上，点云在底座内部以结构体数组分离（SoA）形式存放，x、y、强度分别连续存储，便于向量化处理与批量提交。

降采样上，对点云做体素栅格化，格内保留最近点，将参与绘制的点数控制在 2 万以内，同时保持场景轮廓的可辨识度。

剔除上，以自车为中心建立均匀网格空间索引，按视口范围快速剔除无效点，避免对全量点做逐点判断。

批渲染上，按着色分档将点分组，每组一次性构造绘制批次提交，把绘制调用次数从与点数同阶降为与档数同阶。

着色上，按距离与高度双维度映射到预定义的分档调色板，避免逐点颜色计算与频繁的画笔状态切换。

坐标变换上，维护世界坐标系与屏幕坐标系之间的仿射变换矩阵，缩放与跟随时只更新矩阵参数，不重算点坐标。

#### 5.3.4 车辆运动学模型

采用运动学自行车模型，以前轮转角 δ 与纵向速度 v 为输入，状态量取位置与航向：

ẋ = v·cos θ， ẏ = v·sin θ， θ̇ = v·tan δ / L

其中 L 为轴距。数值积分采用四阶龙格—库塔法以提高大步长下的精度。参数标定取轴距 2.7 m、最大前轮转角 0.6 rad、加速度限幅 -6 至 3 m/s²。

#### 5.3.5 通信网关与协议

采用双通道策略：TCP 承载控制指令、算法输出与结构化状态，可靠性优先；UDP 承载点云数据，时效性优先，允许丢帧。

报文格式为 4 字节长度前缀加 JSON 载荷，长度前缀用于解决 TCP 粘包；每个报文携带单调递增序号与发送时间戳，接收端据此做乱序重排与时延统计。

心跳机制上，算法侧以 10 Hz 发送心跳，底座 500 ms 未收到即判定断线，进入保持模式（暂停物理推演）并等待重连，避免状态错乱。

#### 5.3.6 Python 算法节点

采用双线程结构：I/O 线程负责收发与解析，计算线程负责算法推理，两者通过有界队列传递数据；队列设置长度上限，保证算法变慢时丢弃旧帧而非无限积压，维持控制的实时性。

感知模块对点云做体素下采样后进行欧氏聚类，拟合三维包围盒并估计目标朝向。预测模块对每个跟踪目标采用 CTRV 模型外推未来 3 秒轨迹。规划模块在 Frenet 坐标系下做横纵向解耦采样，以安全性、舒适性与全局路径一致性构成代价函数，选取代价最小的轨迹。控制模块以 PID 跟踪目标速度、以 Stanley 律跟踪参考路径，并预留 MPC 接口用于对比实验。

#### 5.3.7 AI 增强模块：语言驱动场景生成与失效搜索

模块由场景生成与失效搜索两部分组成，均以独立进程实现，通过底座既有的 Socket 通道通信，在配置文件中按需启用。两部分共用一份参数化场景模板的定义，模板既是语言解析的输出，也是失效搜索的输入，从而使"描述—生成—搜索"成为一条链路而非两个孤立的工具。

场景模板包含四组字段：道路几何（车道数、曲率、路口类型）、交通参与者（类型、初始位姿、期望速度）、行为脚本（触发条件、动作类型、持续时间）与环境参数（附着系数、能见度）。字段以 JSON Schema 约束类型、取值范围与必填项。大语言模型接收自然语言描述后输出候选模板，底座侧依次执行结构校验（是否符合 Schema）与语义校验（车距是否为正、触发时刻是否落在仿真时长内、初始位姿是否与其他参与者重叠）。校验失败时将具体的错误信息回填给模型并重试一次；仍失败则回退到最接近的预置模板，并在界面上标出待人工补全的字段。模板复用通信层已有的序列化实现，不额外引入格式转换。

失效搜索在模板给定的参数空间内进行。搜索变量取自车初速、初始跟车间距、旁车切入时刻、路面附着系数与感知噪声强度，每个变量设定上下界与先验分布。评价函数直接取场景仿真结束后的指标：是否发生碰撞、最小碰撞时间（TTC）与最大纵向加速度。由于单次仿真耗时在百毫秒量级、目标函数不可导且含随机噪声，采用贝叶斯优化求解：以高斯过程拟合指标与参数之间的映射，以期望改进作为采集函数选取下一次评估点，迭代预算控制在 100 次以内。Shahriari 等的综述指出，这类基于代理模型的方法在评估代价高、维度中等的黑箱问题上通常显著优于网格搜索与随机采样，这与本场景的约束正好吻合。

两类调用都可能耗时数百毫秒以上，因此模块在设计上被明确隔离于实时链路之外：场景生成只在编辑态触发，此时仿真尚未启动；失效搜索只在批量离线模式下运行，由外部脚本按队列依次提交任务，结果以场景文件与指标表的形式落盘。主循环内部不出现任何对模型的同步等待，十万点量级下的帧率指标因此不受影响。这一约束也决定了两侧的接口形态——底座向模块暴露的是"加载场景文件"与"运行至结束并返回指标"两个原子操作，而非逐帧回调。

## 六、实验方案与评价指标

（1）渲染性能实验。在集成显卡笔记本与嵌入式平台两类环境下，测量不同点云规模（1 万、5 万、10 万点）下的平均帧率、P99 帧时间、单核 CPU 占用与内存峰值。评价指标：十万点量级平均帧率不低于 60 FPS，P99 帧时间不超过 16.7 ms。

（2）通信时延实验。测量算法进程与底座之间的往返时延，统计均值、标准差与 P99，对比 TCP 单通道与 TCP/UDP 双通道两种方案的差异。评价指标：控制回路往返时延均值不超过 5 ms。

（3）回溯一致性实验。在仿真运行中随机选取若干时刻执行回溯，比较回溯前后同一逻辑帧的世界状态。评价指标：位姿偏差不超过 1e-3 m，回溯定位误差不超过 1 个物理步长。

（4）算法闭环精度实验。设计直道跟车、弯道跟踪、前车紧急制动、旁车切入四类场景，测量横向跟踪误差均方根、纵向速度误差均方根、航向角误差与场景通过率。评价指标：直道横向误差均方根不超过 0.15 m，弯道不超过 0.3 m。

（5）横向对比实验。在相同硬件上对比 CARLA、highway-env、CommonRoad 与 ADASim 的冷启动时间、安装体积、最低硬件配置与部署步骤数，以表格形式呈现。

（6）场景生成与失效搜索有效性实验。构造 50 条自然语言场景描述，覆盖跟车、切入、路口冲突、施工绕行与雨雾退化五类工况，统计模板生成的结构合法率、语义合理率与人工修正字段数。在跟车与切入两类模板上，分别以贝叶斯优化与随机采样各运行 100 次仿真，比较二者发现的失效场景数量与最小碰撞时间的下降幅度。评价指标：结构合法率不低于 95%，同等仿真次数下贝叶斯优化发现的失效场景数不少于随机采样的 2 倍。

## 七、可行性分析

（1）技术可行性。所选技术栈均为成熟方案：Qt 提供跨平台的窗口管理、绘图与异步网络能力；C++17 提供足够的运行时性能与现代化语言特性；Python 生态中的 NumPy、SciPy、CasADi 可支撑感知、规划与控制算法。运动学自行车模型、Frenet 采样规划与 Stanley 控制均有公开文献与参考实现，技术路径清晰、风险可控。

（2）条件可行性。开发所需的编译器、Qt 库与 Python 环境均为开源免费，无需商业授权；开发与测试可在普通个人电脑上完成，不需要专用场地或测试车辆；实验对照所需的 CARLA 等平台同样开源，可用于横向比较。

（3）时间可行性。课题周期约六个月。按"最小闭环优先、逐层叠加"的迭代策略，核心闭环可在第四个月完成，第五个月用于 AI 增强模块与性能优化，最后一个月用于实验验证与论文撰写，进度安排具备冗余度。

（4）风险与应对。主要风险有四：一是点云渲染优化不达预期，应对方案是优先保证功能正确，将帧率目标按点云规模分档设定，并保留调节降采样精度的参数；二是跨语言通信在高频下出现时延抖动，应对方案是将点云通道切换为二进制协议以降低序列化开销；三是算法闭环调试耗时超出预期，应对方案是先以 PID 加纯跟踪实现基线闭环，再逐步替换为 MPC；四是 AI 模块依赖外部模型服务，现场演示存在网络与响应时延的不确定性，应对方案是将演示场景全部预生成为本地场景文件，答辩时以离线加载方式复现，不依赖实时调用。
