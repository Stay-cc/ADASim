# 第 3 章 需求分析与总体设计

## 3.1 需求分析

### 3.1.1 功能性需求

平台的目标用户是算法开发者，其典型工作循环是"改一版算法 → 跑一组场景 →
看指标与过程 → 定位问题 → 再改"。六个功能需求直接对应该循环中的动作。

**F1 闭环仿真。** 平台需同时容纳仿真底座与算法进程，两者以约定的通信方式
交换状态、点云与指令，构成"感知—决策—控制—物理"的完整回路。算法进程必须
能独立重启而不影响底座。

**F2 场景化运行。** 场景（道路几何、参与者、初始状态、天气与附着）以声明式
文件描述，可加载、可校验、可批量运行；不允许在代码里硬编码一个场景。

**F3 帧级回放。** 可暂停、可逐帧前进、可拖动到任意历史帧查看当时的完整世界
状态（含点云与算法输出），且回看不破坏记录。

**F4 分支重跑。** 可从历史某帧继续运行，此后原时间线作废。用于反事实实验。

**F5 运行时注入扰动。** 可在运行中向场景注入虚拟目标或改变环境，用于构造
"没在剧本里"的工况；注入必须对算法表现为传感器观测，而不能走真值通道。

**F6 场景生成。** 从自然语言描述生成可加载的场景文件，并对生成结果做结构与
语义校验；无模型可用时降级到规则解析。

### 3.1.2 非功能性需求

非功能性需求是可验证的，每条都给出判据与验证方式。

| 编号 | 需求 | 判据 | 验证方式 |
| --- | --- | --- | --- |
| N1 | 渲染实时性 | 十万点、1280×720 下 P99 帧时间 ≤ 16.7 ms | 离屏基准程序，7 档点数扫描 |
| N2 | 链路时延 | 常规点云规模下控制回路净时延 ≤ 5 ms | 序号回带法测量，统计均值/P99 |
| N3 | 回溯一致性 | 重推演与直跑位姿偏差 ≤ 1e-3 m | 19 个目标帧逐个比对 |
| N4 | 部署门槛 | 无独立显卡可运行，冷启动 ≤ 1 s | 计时打点 + 部署目录体积 |
| N5 | 可回归 | 核心不变量进入自动化测试，全套 ≤ 5 s | CTest |

其中 N2 与 N3 是本文相对于既有平台最强调的两条。它们不是"性能指标"，而是
**可观测性指标**：只有把时延与一致性测出来并且测准，闭环实验的结论才可信。

### 3.1.3 需求之间的冲突

需求并非彼此独立，设计时必须在冲突处做取舍。本平台遇到的四处冲突与解决方式：

1. **保真度 vs 帧率（N1）**。三维渲染 + 传感器物理无法在集显上达到 60 FPS。
   取舍：放弃三维，采用二维鸟瞰 + 扫描线光栅化，把预算留给点云规模。
2. **确定性 vs 实时性（N3）**。确定性要求固定步长、禁止跨线程共享可变状态；
   实时性倾向"能算多少算多少"。取舍：物理固定 50 Hz 推进，渲染按需出帧、
   允许丢帧，但物理步一步不丢。
3. **回看 vs 分支（F3/F4）**。二者对"当前帧"的语义要求相反。取舍：拆成两个
   入口（见 2.5.3），并把"已录末帧"与"当前帧"分成两个概念。
4. **注入的真实性 vs 可控性（F5）**。注入若参与物理推进，会与场景参与者
   互相挤压，产生难以归因的连锁反应。取舍：注入目标不参与物理与碰撞，只
   进点云，因此可以任意重叠、随时清除。

## 3.2 总体架构

### 3.2.1 四层划分

平台分四层，依赖严格单向：

```
L1 表现层    Qt 窗口、视口、交互、HUD          src/presentation
L2 应用层    仿真主控、场景服务、实验编排       src/application
L3 领域层    物理、传感器、时间轴、模型         src/domain      ← 纯 C++17
L4 基础设施  渲染、网络、持久化、时钟、日志     src/infrastructure
```

划分依据不是"文件放哪"，而是**变化的原因**：领域层的变化来自物理与算法语义，
基础设施层的变化来自外部技术选型（换渲染后端、换传输方式），应用层的变化
来自业务流程。把三者混在一起，任何一次技术选型变更都会波及语义代码。

### 3.2.2 依赖规则的强制手段

"领域层不依赖 Qt"如果只写在文档里，三个月后必然被破坏——某次调试中
`#include <QDebug>` 就进来了。平台用两道防线把它变成硬约束：

**配置期字面扫描。** `LayerGuard.cmake` 在 `cmake` 配置阶段递归读取领域层与
应用层源码，一旦出现 `#include <Q...` 或 `#include "infrastructure...`，
直接 `FATAL_ERROR` 并指出文件与处理建议。成本几乎为零，但把"事后 code review"
提前到了"配置即失败"。

**链接期符号隔离。** `adasim_domain` 目标不链接 Qt6，任何 Qt 符号的引用都会
在链接阶段失败。字面扫描可以被宏或间接包含绕过，链接失败绕不过去。

两道防线的收益是可验证的：同一套领域层既能驱动 Qt 界面（`adasim`），也能
编译成完全无 Qt 的 `adasim_headless`，后者跑完 1500 步（30 s 仿真）只需
126 ms，可作为回归探针与性能基线。若无分层强制，这个目标不可能存在。

### 3.2.3 五个端口与装配根

层与层之间只通过接口通信。平台定义五个端口，全部位于领域层：

| 端口 | 职责 | 实现 |
| --- | --- | --- |
| `IClock` | 单调时钟与纳秒计时 | `SteadyClock`（测试用 `FakeClock`） |
| `IRenderPort` | 提交快照、请求出帧 | `QtRenderer`（离屏基准另有实现） |
| `ITransportPort` | 发布点云/状态、轮询指令 | `TcpUdpGateway`（测试用记录替身） |
| `IPersistence` | 场景存取 | `JsonScenarioRepository` |
| `ILogger` | 分级日志 | `ConsoleLogger` |

端口的价值在测试里最直观：`tests/` 下的用例用 `FakeClock` 手动拨表、用
`RecordingTransport` 记录发布内容，于是"注入后点云里有没有点""真值里有没有
它"这类断言可以在毫秒级完成，不需要起网络、不需要等真实时间。

所有这些实现只在**一个文件**里装配：`src/main.cpp`。它是整个工程唯一同时
包含应用层与基础设施层头文件的地方。这一约束让"换掉 Qt"或"换掉 TCP"的改动
被限制在一个函数体内，而不是散落全工程。

### 3.2.4 线程模型

平台有三个执行体：

1. **主线程（GUI + 物理）**：定时器按 20 ms 节拍推进物理、发布报文、刷新
   界面标签。物理放在主线程而不是独立线程，理由是可复现性——独立线程会引入
   调度抖动，同一段轨迹两次运行可能在不同步被渲染线程打断，虽然不影响结果，
   但会让"帧号—墙钟"的对应关系不稳定，不利于时延分析。
2. **渲染线程**：`QtRenderer` 内部线程，从队列取快照、光栅化、发信号回主线程
   贴图。渲染与物理解耦（"算绘分离"）是本平台帧率能达标的关键：点云生成在
   物理线程，光栅化在渲染线程，两者不互相等待。
3. **通信**：TCP/UDP 的收发由 Qt 事件循环驱动，不做阻塞读取。

### 3.2.5 单写多读快照

跨线程共享状态是本类系统最容易出错的地方。平台采用"单写多读 + 不可变快照"：
物理线程是唯一写者，写完后构造一个 `WorldSnapshot`（含点云与状态），以
`shared_ptr<const T>` 交给渲染线程。渲染线程只读，不需要加锁；快照本身不可变，
所以不存在"渲染到一半状态被改"的问题。

快照的构造是**惰性**的：只有状态推进过才重新采样。渲染与点云发布各有自己的
节拍（前者按屏幕刷新、后者 10 Hz），若每步都无条件重采，十万点下等于每秒多
做几十次无用功。这个优化在架构上是必要的而非可选的：十万点的点云采样约
0.5 ms，50 Hz 下就是 2.5% 的预算。

## 3.3 通信协议设计

### 3.3.1 为什么分成两条通道

状态与点云的特性完全不同，混在一条通道里会互相拖累：

- **状态报文**：低频（50 Hz）、小（几百字节到几十 KB）、必须可靠有序——
  丢一帧就会导致指令与状态错配。
- **点云报文**：高频（10 Hz）、大（十万点约 1.18 MB）、允许丢帧——感知算法
  对单帧丢失不敏感，但绝不能因此阻塞。

因此状态与指令走 TCP（4 字节大端长度前缀 + 紧凑 JSON），点云走 UDP 分片
（24 字节头 + 12 字节点记录）。JSON 而非二进制状态报文的选择是有意的：
字段可读、可增删、调试时能直接看，而状态报文体积小，解析开销可忽略。

### 3.3.2 分片与重组

UDP 单包受 MTU 约束，十万点必须分片。平台按每片 120 点（1440 字节载荷）
切分，凑上 24 字节头正好 1464 字节，留出 IP/UDP 头的余量。分片头包含
`chunkIndex/chunkCount/frameId/simTime/count` 与一个"帧尾"标志位，接收侧据
`chunkCount` 判断是否收齐。

这里的关键决策是**不做丢片重传**：重传会让点云延迟不确定，破坏"当前帧点云
对应当前状态"的时序假设。丢片时整帧废弃，感知沿用上一帧结果——这个选择在
第 5 章的 E2 实验里得到验证：十万点连续发送时零丢片。

另一个决策是**重组推迟到整帧收齐**。早期实现逐片解包再拼接，十万点等于
十万次 Python 层循环，单帧 32.6 ms，占净时延的三分之一。改为"分片只切头、
载荷暂存、整帧一次性批量解码"后降到 2.6 ms。这条经验说明：协议设计的性能
问题不一定在协议本身，而在接收侧的解析粒度。

### 3.3.3 时延测量：序号回带

底座测不到"算法进程处理了多久"，算法进程也测不到"底座何时消费了指令"。
平台的解法是让指令带自增 `seq`，底座在**下一帧状态**里回带最近消费的
`ackSeq`；算法进程据此用"发出时刻 → 收到回带"计算往返时延，两端各用自己的
单调时钟，不需要时钟对齐。

这个量必然包含一个状态帧周期（指令只能在下一帧状态被回带），因此报告时
同时给出"往返时延"与"净时延 = 往返 − 实测帧周期"。帧周期取实测 EMA 而不是
写死 20 ms：底座改步长或改发布频率时，写死的那份会静默算错。

## 3.4 时间轴与回溯设计

### 3.4.1 覆盖式单时间轴

平台只有一条时间轴，回溯到历史帧后继续运行会**覆盖**其后的记录，而不是
分叉出新的时间轴。这个选择牺牲了"同时保留多个分支"的能力，换来的是内存
可控与语义简单：任何时刻只有一条有效轨迹，界面上的进度条也只有一个。

若要做分叉，代价是每条分支都要独立的缓冲区与快照链，且用户需要理解"当前
在哪条分支上"。对本平台的目标用户（单人调试算法）而言，这个复杂度不值得。

### 3.4.2 三级缓冲状态

时间轴上有三个位置需要区分，混用会导致一类典型 bug：

- **写指针（已录末帧）**：缓冲里最新的一帧，决定进度条上限。
- **当前帧**：正在显示与推进的那一帧，回看时会小于写指针。
- **窗口起点**：环形缓冲能回看到的最早一帧。

早期实现只用一个"当前帧"，回看后进度条上限跟着缩短，用户越拖范围越小。
拆成三个量后，回看与继续推进的语义才清晰。

## 3.5 场景描述格式

场景用 JSON 描述，字段分三组：路形（车道数、车道宽、曲率、附着、能见度）、
参与者（类型、初始位姿、速度、行为模板与参数）、传感器（量程、采样密度）。

选择 JSON 而非领域专用格式的理由是可校验性与可生成性：JSON Schema 能对
结构做机器校验，大语言模型也更容易稳定地生成 JSON。代价是体积与可读性不如
YAML，但对几十行量级的场景文件不构成问题。

格式设计中有一条容易忽略的约束：**校验必须能识别"写漏了参与者"这类错误**。
因此校验规则要求普通场景至少有一个交通参与者，同时为沙盒场景保留一个显式
开关 `openWorld`——这个开关不能推广成"允许空参与者列表"，否则写漏了场景
也查不出来。

## 3.6 本章小结

本章给出了平台的功能与非功能需求、四处需求冲突的取舍、四层架构与依赖强制
手段、五个端口与装配根、线程模型与快照并发策略、双通道协议与分片设计、
时间轴的三级状态，以及场景格式的校验约束。

贯穿这些决策的一条主线是：**把"可复现"和"可观测"当作一等需求**。物理放主
线程、步长固定、指令按帧记录，都是为了复现；序号回带测时延、失联与兜底
分列两个状态位、回看与分支拆成两个入口，都是为了可观测。这两件事在多数
平台里是"用户自己想办法"，本文把它们做进了架构。
