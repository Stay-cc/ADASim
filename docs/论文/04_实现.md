# 第 4 章 关键模块实现

本章按"问题—方案—代价"说明七个关键模块的实现。所有数字均来自本机实测，
出处见第 5 章与 `docs/实验报告.md`。

## 4.1 确定性物理推进

### 4.1.1 纯函数形状的推进器

`PhysicsEngine::step(state, dt, cmd)` 的签名是三个输入、一个输出，不读写任何
成员的可变状态。这一形状不是风格偏好，而是回溯能力的必要条件：重推演与
在线推进必须走**同一条代码路径**，否则两条路径的任何差异都会在回溯结果里
表现为偏差，而这种偏差极难定位。

实现上，自车状态按 RK4 推进：

```cpp
const Derivative k1 = evaluate(pose, speed, steer, L);
const Derivative k2 = evaluate(advance(pose, k1, dt * 0.5), speed, steer, L);
const Derivative k3 = evaluate(advance(pose, k2, dt * 0.5), speed, steer, L);
const Derivative k4 = evaluate(advance(pose, k3, dt), speed, steer, L);
return combine(pose, k1, k2, k3, k4, dt);
```

四步求值都用同一个 `steer` 与 `speed`——即在步内冻结控制量。这是"零阶保持"
假设，与真实执行器"一个控制周期内保持不变"的语义一致，也保证了控制量在
步内的因果顺序无歧义。

### 4.1.2 纵横向的耦合与解耦

纵向加速度先积分出速度，再用于横向积分。顺序不能反：若先用旧速度算完位置
再更新速度，车辆在加速时每步都会"少走一点"，表现为里程系统性偏短。这一
顺序在 `step` 里被固定下来，重推演时也必须一致。

参与者（非自车）的推进要简单得多：按各自速度沿航向匀速前进。跟驰、切入、
制动三类模板在行为层改写速度与航向，物理层只负责位移。把行为与位移分开的
好处是行为可以"回退"——切入进度作为状态的一部分存入缓冲，回溯时跟着回退，
这一点在第 5 章的 E3 实验里被验证（参与者状态也逐位一致）。

### 4.1.3 指令时延的处理

算法进程的指令到达时刻与物理步的边界不对齐。平台的策略是：指令一到就写入
"最近一条有效指令"，物理步只读这个槽位。因此一条指令生效的延迟取决于它
落在哪个 20 ms 步内，平均 10 ms。这层延迟是真实存在的（真实系统也有总线
与执行器延迟），不应被消除；但必须在时延统计里被识别，否则会被误算成通信
开销——这也是 3.3.3 要单独给出"净时延"的原因。

## 4.2 点云生成与"雷达欺骗"注入

### 4.2.1 采样与衰减

`LidarModel::sample` 遍历状态中的障碍物，对每个包围矩形沿四条边按
`1/pointsPerMeter` 的间距取点，按到自车的欧氏距离做线性衰减，低于阈值的
强度被抬到下限（避免远处目标点强度为零而被算法当作噪声）。

一次采样要处理十万点时，逐点计算 `hypot` 会成为热点。实现上把量程比较改为
平方比较、把 `cos/sin` 提到边循环外，采样耗时从 0.9 ms 降到 0.49 ms。

### 4.2.2 注入通路：只进点云，不进真值

注入功能的核心是一条**数据分流**：注入目标存于 `WorldState::ghosts`，
`LidarModel` 对它做与真实障碍物完全相同的轮廓采样，但 `publish()` 只把
`state.obstacles` 写进状态报文，`ghosts` 一个字都不发。

```cpp
for (const auto& e : state.obstacles) { emitOutline(...); }
for (const auto& e : state.ghosts)    { emitOutline(...); }   // 同一条采样
```

若注入目标也进真值列表，算法只要直接用真值就能"看见"它，这条通路检验的
就不再是感知链路，而成了一个假测试。因此代码里对这条边界有专门的断言型
测试（`tests/sandbox_check.cpp`）：注入后点云必须有点、真值列表必须不含它。

### 4.2.3 为什么不参与物理

注入目标没有碰撞体，也不会被自车推动。这意味着自车可以直接从它"身上"开
过去。这个反直觉的行为是有意的：若注入目标参与碰撞，一次实验失败可能来自
"注入位置不合适"而非算法问题，归因变复杂；而保持"幽灵"语义后，注入只影响
观测，失败原因只可能是感知或决策。

代价是演示时的观感——算法离线时车会穿过虚线框。这一点在 README 里被明确
写出，并且作为"感知链路确实在工作"的对照：算法在线时车会停，离线时会穿过。

## 4.3 时间轴缓冲与回溯

### 4.3.1 环形缓冲与快照间隔

缓冲容量 1500 帧（30 s），每 25 帧（0.5 s）存一份完整快照。选择这两个数字
的依据是内存与重推演长度的乘积：

- 单帧状态约 420 字节（自车 + 少量参与者），1500 帧约 0.63 MB；
- 快照间隔 25 帧时，最坏重推演 24 步，实测 0.009 ms。

若把间隔改成 5 帧，内存升到约 3 MB，重推演降到 4 步——没有意义，因为
0.009 ms 已经在噪声量级；若改成 250 帧，内存只省一点，重推演升到 250 步
（约 0.09 ms），仍可接受但余量变小。25 帧落在"两边都不紧张"的中段。

### 4.3.2 回溯的三步

```
planSeek(target) → 找最近的快照 → 从快照重推演至 target
```

重推演时使用的指令**不是**重新向算法索取的，而是从缓冲记录里读回该帧自车
实际执行的转角与加速度。这是保证一致性的关键：若重推演时去问算法，算法的
输出可能已经变了（模型更新、随机性、甚至进程重启），结果必然不一致。

实现中还处理了一个边界：回溯到第 $n$ 帧时，缓冲里第 $n$ 帧之后的数据不能
立即删除——用户可能只是"看一眼"。因此 `previewSeek` 只改当前帧、不动写指针；
只有用户从历史位置**继续播放**时，才把写指针回退到该帧（`seek`/`start`），
此后新推进的帧覆盖旧数据。

### 4.3.3 一个新旧语义的副作用

"继续播放即分支"带来一个界面上的细节：从历史位置按播放后，进度条会立刻
缩短到当前位置。若不提示，用户会以为记录丢了。实现上在状态栏给出"已从第
N 帧分支"的提示，并在工具栏区分"回到最新"（跳回写指针）与"播放"（从当前
帧继续）两个动作。

## 4.4 渲染管线

### 4.4.1 算绘分离

渲染分两段：物理线程生成点云并构造快照，渲染线程光栅化。两段之间只有一次
`shared_ptr` 的所有权转移，没有锁。

这一分离解决的是一个具体的性能问题：十万点的一次采样约 0.49 ms，光栅化约
4.2 ms（含 792 个车体）。若两者在同一线程串行，采样时间会直接压在帧时间上；
分开后渲染线程只在有新快照时工作，物理线程的节拍不受画面刷新影响。

### 4.4.2 扫描线写点云

逐点调用 `drawPoint` 在十万点下实测 60~90 ms，完全不可用。平台改为直接写
扫描线缓冲：把点按整型屏幕坐标写入预分配的像素数组，最后一次性转成 `QImage`。
十万点段耗时降到 0.40 ms/帧（每百点 0.4 µs），比逐点绘制快两个数量级。

整帧耗时的大头其实不是点云而是**画车**：十万点档的 4.22 ms 里有 3.8 ms 花在
792 个圆角矩形的抗锯齿绘制上。真实交通在 50 m 量程内只有几十辆车，这部分
不到 0.3 ms。压测数字之所以"看起来慢"，是因为它用了合成密排车阵——这一点
在第 5 章的口径说明里被单独指出。

### 4.4.3 图层顺序与弯道车道线

绘制顺序固定为：网格 → 路面 → 车道线 → 路缘 → 点云 → 车体 → 注入目标 →
HUD。顺序错了会出现"点云被路面盖住"这类问题，而这类问题在深色背景下不易
察觉，因此顺序在代码里被写成注释显式约定。

车道线在弯道上按圆弧采样绘制，圆心为 $(0, 1/\kappa)$、半径为 $1/|\kappa|$，
与第 2 章的参考路径同一套几何。早期版本用直线画车道线，弯道场景里会出现
"车道线是直的、车在弯"的错配，视觉上像渲染 bug，实际是几何不一致。

## 4.5 算法进程

### 4.5.1 单线程事件循环

算法进程用单线程事件循环而非收发分离的双线程。理由是因果顺序：单线程下
"收到一帧状态 → 算一次 → 回一条指令"的先后关系天然成立，不会出现指令与
状态错配；而分线程要加锁或拷贝，收益（并行收发）在环回场景下几乎为零。

循环用 `selectors` 同时监听 TCP 与 UDP，一次唤醒处理所有就绪事件，然后按
"先状态、后点云"的顺序处理——状态决定自车位姿，点云必须在其后解释。

### 4.5.2 感知与跟踪

感知模块把点云聚类成框（2.4 节），跟踪器做最近邻关联并用 $\alpha$-$\beta$
滤波估计速度。这里有一处必须小心：滤波的时间基准要用**点云自带的仿真时间**，
不能用墙钟。状态帧会成簇到达（一次 `select` 可能取出好几帧），若用墙钟做
$\Delta t$，两帧可能只差 0.2 ms，而 $\beta/\Delta t$ 会把几厘米的残差放大成
几十 m/s 的速度尖峰，航迹随即被外推到自车跟前，触发一次假紧急制动。

### 4.5.3 决策与控制

决策层用 IDM 计算纵向加速度，用走廊占用法则选前车（2.2.2）。横向用 Stanley
律加曲率前馈（2.3.2），输出经一阶惯性环节近似转向执行器。

几个工程细节直接影响闭环精度：

- **车距按保险杠算**：$s = \Delta x - \tfrac{1}{2}(L_{\text{ego}} + L_{\text{lead}})$。
  用中心距会系统性高估车距。
- **前车速度投影到自车纵轴**：横向速度不参与跟驰，否则切入过程中会出现
  莫名其妙的减速。
- **稳态误差统计要跳过 warmup**：底座先启动、算法后接入，接管前那段自车
  是匀速直行的，把它算进横向误差，量到的是接管延迟而非跟踪质量。

### 4.5.4 断链兜底

算法进程缺席时，底座的 `StandbyGuard` 接管纵向控制。控制律是连续的两层：

1. **车距层**：把净距拉回 $s_0 + h\cdot v$（$s_0=3$ m，$h=1.5$ s），比例 +
   阻尼，车距有余量时输出为零；
2. **硬制动层**：TTC 进入 1.2 s 以内时，改用"以当前净距刚好停住"所需的
   减速度。

两层取更狠者，再经 8 m/s³ 的加加速度限制落到指令上。之所以不用"阈值 + 锁存"：
锁存能压住点刹，但一旦介入就恒定满刹；纯阈值每帧重算又会抖成点刹。连续律
加变化率限制让介入与退出都是斜坡。

一个关键的接口设计是：兜底只在**无客户端在线**时介入。算法一旦接入，纵向
控制权完全归它，底座不替算法踩刹车——否则感知失效、决策振荡这类本该暴露
的问题会被兜底逻辑悄悄抹平，闭环对比实验就失去意义了。

### 4.5.5 "在线"与"在制动"必须分开

断链判据用的是"有没有客户端"，而不是"有没有在制动"。原因很实际：断链时若
车距还有余量，兜底律不会制动，此时若用"在制动"作为断链判据，就会把"离线但
没刹"读成"在线"。因此状态报文里 `link`（链路）与 `standby`（兜底介入）是
两个独立字段，界面上的角标也按三态显示：算法未接入、离线兜底制动中、离线但
车距有余量。

## 4.6 场景生成

### 4.6.1 生成通路

自然语言描述经大语言模型转成场景 JSON，再经三层校验：结构校验（字段与类型）、
语义校验（数值范围与物理合理性）、可加载校验（仓储能否解析并构造世界）。
无密钥时降级到规则解析：用关键词匹配路形与行为模板。

### 4.6.2 校验为什么必须分层

只做结构校验会放过"数值荒谬"的场景，例如曲率 5 m⁻¹（转弯半径 0.2 m）、
附着系数 3.0、参与者初始位置在雷达量程外。只做语义校验会放过"字段名拼错"
这类问题，而那恰恰是模型最常犯的错。三层校验的顺序也不能变：结构错了，
语义校验没有意义；语义错了，加载一定失败。

### 4.6.3 回退机制

当描述超出模板表达能力时（例如"路口左转与直行车流冲突"），生成器**回退**到
最接近的模板并标记 `fallback: true`，而不是产生一个非法场景。50 条描述的实测
回退率为 24%，这个比例是后续扩展模板的直接依据——回退不是错误，但它精确地
度量了"模板表达能力与真实场景需求之间的差距"。

## 4.7 交互与 HUD

### 4.7.1 右键注入的坐标换算

视口支持缩放与平移，右键位置是控件像素坐标，必须反算成世界坐标再注入。
换算矩阵由视口的“中心 + 每米像素数”决定，实现为 `pixelToWorld`。这里容易
出错的是缩放方向：屏幕 y 轴向下、世界 y 轴向上，漏掉符号翻转会把目标注入到
镜像位置——看起来"点哪哪不对"，实际是坐标变换错。

### 4.7.2 HUD 的字段选择

HUD 显示七组量：车速、帧率与光栅化耗时、往返时延与指令龄、算法三态、决策
原因与纵向/横向指令、注入目标数、点云数。选择标准是"能否帮助定位一次异常"：

- 车速与指令对不上 → 看指令龄与时延；
- 车没减速 → 看决策原因与点云数（是没检出还是没决策）；
- 完全不动 → 看算法三态（是离线还是算法输出为零）。

这七组量在演示与调试中反复用到，因此被做成一屏可见，而不是藏在多个面板里。

## 4.8 可回归性与实验编排

### 4.8.1 把不变量钉进测试

平台的回归测试不是"跑一遍看看"，而是把几条**关键不变量**写成断言，任一条
失败即视为功能被破坏。当前 7 个用例，标签分为 unit / python / integration：

| 用例 | 断言的不变量 | 类型 |
| --- | --- | --- |
| `standby_guard_check` | 断链后能以不追尾的方式停住；车距有余量时不介入 | unit |
| `cut_in_check` | 切入车进入走廊后被识别为前车并减速 | unit |
| `replay_check` | 19 个目标帧的重推演与直跑逐位相等 | unit |
| `sandbox_check` | 注入目标进点云、不进真值、回看时消失、清除后归零 | unit |
| `headless_closed_loop` | 无界面底座能独立闭环 1500 步并给出统计 | integration |
| `algo_selftest` | 协议编解码、聚类、跟随减速、走廊过滤、纠偏方向 | python |
| `ai_selftest` | 场景生成的结构/语义/可加载三层校验 | python |

设计上有两条刻意的选择。

其一是**不用正则匹配输出**。CTest 提供 `PASS_REGULAR_EXPRESSION`，只要输出里
出现某个字符串就算通过——这会掩盖"程序崩溃但先打印了成功字样"的情况。平台
的用例全部以退出码为准，失败信息打到 stderr。

其二是**测试用替身而不是真实环境**。用例用 `FakeClock` 手动拨表、用记录式
传输替身截获发布内容，因此全套测试 1.35 s 跑完，可以进 CI；若依赖真实计时
与网络，单是用例之间的端口占用就会带来不稳定。

### 4.8.2 实验编排

五组实验的编排脚本（`tools/run_experiments.py`）负责"起底座 → 等监听 → 起
算法 → 收汇总 → 落盘"。它解决的是**可比性**问题：

- 每组的巡航车速取自场景文件的 `egoSpeed`，而不是统一写死。否则跟驰场景会
  因为巡航设得比前车高而一直顶着前车跑，量到的不是跟驰质量；
- warmup 按场景单独指定。切入发生在 3~5 s，若统一取 5 s 就会把切入过程本身
  排除在统计之外；
- 底座比算法进程多跑 4 s，保证最后一帧点云能被消费完，否则结束时的统计会
  少一截。

### 4.8.3 基准程序与离屏测量

渲染性能不能在带界面的程序里测：窗口刷新、事件循环与垂直同步都会污染数据。
平台单独提供 `adasim_bench`（只链接领域层与基础设施层，不创建窗口），对同一
场景重复采样并输出中位/p95/p99。这样测到的是"光栅化 + 点云采样"的真实成本，
与界面无关，也便于在不同机器上复现。

## 4.9 本章小结

本章说明了七个模块的实现，其中反复出现的一条经验是：**性能问题常常不在
看起来最贵的地方**。十万点渲染的瓶颈是画车而不是点云；十万点时延的瓶颈是
逐点解包而不是网络；回放失效的根源是"当前帧"与"已录末帧"混用而不是缓冲
结构。这些问题只有在把每一段单独测出来之后才会暴露，因此平台把分段计时
（点云采样、光栅化、单帧计算、往返时延）做成了常驻输出。
