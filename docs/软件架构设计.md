# ADASim 软件架构设计（分层架构）

## 1 设计目标与约束

分层不是为了把文件放进不同文件夹，而是为了回答一个问题：**当某一处需要变化时，变化会扩散到多远。** 本平台的四类变化源各自频率不同：

| 变化源 | 变化频率 | 期望影响范围 |
| --- | --- | --- |
| 渲染实现（QPainter → OpenGL） | 低，但一旦发生则牵动全局 | 应只影响一个实现类 |
| 通信协议（JSON → 二进制） | 中 | 应只影响网关与编解码 |
| 算法本身（PID → MPC） | 高 | 应完全不进入底座 |
| 场景与实验设计 | 最高 | 应不触碰任何核心类 |

若不做分层，这四类变化会共同汇聚到一个"上帝类 Simulator"里，最终演化为改一处、崩三处的局面。分层的作用就是把这四条影响链切开。

约束条件沿用开题报告：单机、无独立显卡、50 Hz 物理步进、十万点云 60 FPS、支持运行中任意时刻回溯、算法进程可独立替换。

## 2 层次划分

平台在进程内划分为四层，另有一组横切关注点。分层的依据是**抽象级别与变化原因**，而非代码行数。

### 2.1 各层职责

| 层 | 职责 | 允许依赖 | 严禁出现 |
| --- | --- | --- | --- |
| L1 表现层 | 窗口、视口、控件、输入事件与用户命令的采集 | L2 应用层；L3 的只读数据类型与端口接口 | 直接 `new` L4 的具体类；持有 `Simulator` 全局单例 |
| L2 应用层 | 用例编排：播放/暂停/倍速/回溯、场景加载与校验、批量实验 | L3 领域层 | 任何 Qt 绘图与网络 API；物理计算公式 |
| L3 领域层 | 世界状态、时间轴、运动学、传感器模型、端口声明 | 仅 C++ 标准库与自带几何工具 | Qt、网络、文件、JSON 库 |
| L4 基础设施层 | 端口的具体实现：渲染、网络、持久化、时钟、日志 | L3 的端口接口 | 反向依赖 L1/L2；领域规则判断 |
| 横切 | 依赖注入装配、配置、日志、性能计数、异常兜底 | 各层的接口 | 业务逻辑 |

### 2.2 依赖规则

依赖方向自上而下，但**只有 L1→L2→L3 是普通的编译期依赖**。L3 与 L4 之间是倒置的：L3 声明端口（纯虚接口），L4 实现端口，谁都不需要知道对方的存在，二者在 `main()` 中由装配代码连接。

这条规则的实际含义是：**`src/domain/` 目录下不允许出现 `#include <QWidget>`、`#include <QTcpSocket>`、`#include <nlohmann/json.hpp>`。** 领域层只用 `std::vector`、`std::array`、`std::optional`、`<cmath>`。

### 2.3 为什么领域层必须与 Qt 绝缘

三个具体收益：

1. **可测试**。`TimelineBuffer` 的回溯一致性、`KinematicBicycle` 的积分精度，可以用普通单测在毫秒级跑完，不需要创建 `QApplication`，也不需要开窗口。若领域层依赖 Qt，测试就得跑在带显示环境里，CI 无法执行。
2. **可移植**。算法验证实验需要跑在无显示服务器的嵌入式板卡上（批量失效搜索就是这种场景），此时不需要链接任何 GUI 库。
3. **可约束**。领域层编成独立静态库且不链接 Qt，**编译器会替你执行分层规则**——一旦有人偷偷引入 Qt 符号，链接阶段直接失败。这比写进文档靠人自觉可靠得多。

## 3 端口定义

端口是分层架构中唯一被允许的"反向"通道，数量必须克制。本设计只保留五个。

```cpp
// src/domain/port/IClock.h
#pragma once
#include <cstdint>

namespace adasim::domain {

struct IClock {
    virtual ~IClock() = default;
    virtual double simSeconds() const noexcept = 0;   // 仿真时钟
    virtual std::uint64_t frameId() const noexcept = 0;
    virtual void advance(double dt) = 0;              // 供回溯重推演使用
};

}  // namespace adasim::domain
```

```cpp
// src/domain/port/IRenderPort.h
#pragma once
#include <memory>
#include "domain/model/WorldSnapshot.h"
#include "domain/model/Viewport.h"

namespace adasim::domain {

struct IRenderPort {
    virtual ~IRenderPort() = default;
    // 只读快照，共享所有权，避免 50 Hz 下的深拷贝
    virtual void submit(std::shared_ptr<const WorldSnapshot> snap) = 0;
    virtual void setViewport(const Viewport& v) = 0;
    virtual void requestFrame() = 0;
};

}  // namespace adasim::domain
```

```cpp
// src/domain/port/ITransportPort.h
#pragma once
#include "domain/model/Packet.h"
#include "domain/model/ControlCommand.h"

namespace adasim::domain {

struct ITransportPort {
    virtual ~ITransportPort() = default;
    virtual void publishCloud(const PointCloudPacket& p) = 0;   // UDP，允许丢
    virtual void publishState(const StatePacket& p) = 0;        // TCP，可靠
    virtual bool pollCommand(ControlCommand& out) = 0;          // 非阻塞
    virtual bool linkAlive() const noexcept = 0;                // 心跳状态
};

}  // namespace adasim::domain
```

另两个端口按同样方式声明：`IPersistence`（场景与回放的读写）、`ILogger`（分级日志）。

## 4 依赖注入与装配

所有具体类型只在 `main.cpp` 出现一次，这个位置称为装配根（Composition Root）。它是全工程唯一知道"谁实现谁"的地方。

```cpp
// src/main.cpp
#include <QApplication>
#include "application/SimController.h"
#include "domain/simulation/PhysicsEngine.h"
#include "domain/timeline/TimelineBuffer.h"
#include "infrastructure/render/QtRenderer.h"
#include "infrastructure/net/TcpUdpGateway.h"
#include "infrastructure/persist/JsonScenarioRepository.h"
#include "presentation/MainWindow.h"

int main(int argc, char** argv) {
    QApplication app(argc, argv);

    const SimConfig cfg = SimConfig::fromFile("config/sim.toml");

    // L4：实现端口
    QtRenderer              renderer(cfg.render);
    TcpUdpGateway           gateway(cfg.net);
    JsonScenarioRepository  scenarios(cfg.paths);
    SteadyClock             clock;

    // L3：纯领域对象，只吃接口与值类型
    PhysicsEngine  physics(cfg.vehicle);
    TimelineBuffer buffer(cfg.window.frames, cfg.window.snapshotEvery);

    // L2：编排，不关心实现
    SimController controller{physics, buffer, gateway, clock};
    ScenarioService scenarioService{scenarios, controller};

    // L1：只拿到门面
    MainWindow window{controller, scenarioService, renderer};
    window.show();

    return app.exec();
}
```

注意 `controller` 构造时传入的是 `gateway`（`ITransportPort&`），而不是 `TcpUdpGateway`。想把 TCP 换成共享内存或进程内直连，只需在装配根换一行、再写一个实现类，L2 与 L3 一行不动。

## 5 分层在运行时的投影

层次是静态结构，线程是动态结构，两者必须对应，否则分层会退化为装饰。

| 线程 | 所属层 | 读 | 写 |
| --- | --- | --- | --- |
| 物理线程 | L3 | 环形缓冲（自身写指针） | 世界状态、环形缓冲 |
| 渲染线程 | L4 实现，L3 端口 | 最新快照（只读） | 离屏图像 |
| 网络 I/O 线程 | L4 | 无 | 控制指令槽位（原子替换） |
| GUI 线程 | L1 | 快照统计量、控制器状态 | 用户命令队列 |

核心约束是**单写多读**：`TimelineBuffer` 只有物理线程一个写者，其余线程拿到的是 `shared_ptr<const WorldSnapshot>`。这从根上消除了"渲染线程与物理线程竞争"这个问题（开题报告 4.1 第 2 条），而不是靠加锁去掩盖它。

### 5.1 一次步进的调用路径

```
物理线程（每 20 ms）
  ├─ clock.advance(dt)
  ├─ controller.consumeCommand()          ← 网络线程投递，非阻塞取走
  ├─ physics.step(state, dt)              ← L3，RK4 积分
  ├─ buffer.append(state)                 ← 写环形缓冲
  └─ gateway.publishState(packet)         ← 端口，L4 TCP

渲染线程（跟随屏幕刷新）
  ├─ snap = buffer.latest()               ← 只读
  ├─ renderer.submit(snap)                ← 端口，L4 批渲染
  └─ emit frameReady(QImage)              ← GUI 线程仅贴图
```

### 5.2 回溯的调用路径

```
GUI：时间轴拖动 → controller.seek(frameId)
  ├─ buffer.at(frameId)
  │    ├─ 命中完整快照 → 直接返回
  │    └─ 命中增量帧   → 从最近快照起重推演（在物理线程内执行）
  ├─ 暂停写指针前进，保留其后的帧以便"前进重放"
  └─ renderer.submit(回溯后的快照)
```

这里有一处容易出错的设计点：回溯后若继续仿真，是覆盖后续帧还是从回溯点分叉？本平台选择**覆盖**（单时间轴模型），因为算法调试的典型动作是"改参数 → 从回退点重跑"，分叉会让时间轴语义复杂化。该选择在论文中应明确写出，并作为与离线录制回放方案的差异点。

`render/` 下只有 `QtRenderer` 一个文件，是有意为之：批构建、降采样、空间剔除的变化原因相同，都属于"如何把点画出来"，拆成三个类只会引入虚调用、拖慢单帧预算（见第 6 章末段）。`persist/` 同理，JSON 编解码与结构校验共享同一份字段表，拆开反而要维护两处映射。

`headless/` 是可执行目标而非库，它证明了分层的实际效果：**不装 Qt 也能把整条算法链路跑完**。若哪一天 L3 偷偷引入了 Qt，这个目标会第一个编译失败。

`python/` 与 `ai/` 是独立进程，不参与 C++ 的层划分；它们与底座之间只有一份报文协议。因此"分层"在此处退化为"协议约定"——这是进程边界带来的天然解耦，也解释了为什么算绘分离能支撑算法独立替换。

## 7 用构建系统强制分层

分层架构最常见的死因是：写的时候分了，三个月后有人为了省事在 L1 里直接 `#include` 了渲染器实现。靠 code review 无法长期维持，靠构建系统可以。

```cmake
# 领域层：不含 Qt，任何 Qt 符号进入都会在链接期失败
add_library(adasim_domain STATIC ${DOMAIN_SRCS})
target_include_directories(adasim_domain PUBLIC ${CMAKE_SOURCE_DIR}/src)
target_compile_features(adasim_domain PUBLIC cxx_std_17)
# 注意：此处刻意不 find_package(Qt6)

# 应用层：只依赖领域层
add_library(adasim_app STATIC ${APP_SRCS})
target_link_libraries(adasim_app PUBLIC adasim_domain)

# 基础设施层：实现端口，可以依赖 Qt
add_library(adasim_infra STATIC ${INFRA_SRCS})
target_link_libraries(adasim_infra PUBLIC adasim_domain Qt6::Widgets Qt6::Network)
set_target_properties(adasim_infra PROPERTIES AUTOMOC ON)

# 可执行程序：装配根把三层连起来
add_executable(adasim ${PRES_SRCS} src/main.cpp)
target_link_libraries(adasim PRIVATE adasim_app adasim_infra)
set_target_properties(adasim PROPERTIES AUTOMOC ON)   # 表现层有 Q_OBJECT，漏掉会报 vtable 未定义

# 无 Qt 也可以构建的闭环，用作分层未被破坏的探针
add_executable(adasim_headless src/headless/main_headless.cpp)
target_link_libraries(adasim_headless PRIVATE adasim_app adasim_domain)
```

除上述目标外，`cmake/LayerGuard.cmake` 在配置阶段做一次字面扫描：领域层与应用层的任何源文件里只要出现 `#include <Q`、`#include "infrastructure"` 等片段，`cmake` 就直接失败并打印违规文件与行号。这是第一道防线，链接期是第二道。

这样划分后，`adasim_app` 根本看不到 `adasim_infra`，L2 想 `#include` 渲染器会直接编译失败。规则由编译器执行，不需要文档约束。

### 7.1 构建与验证

```bash
# 完整构建（需 Qt6 >= 6.2）
cmake -S . -B build -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release
cmake --build build -j

# 精简构建：只出领域层、应用层与无界面闭环
cmake -S . -B build -DADASIM_WITH_GUI=OFF
cmake --build build -j

# 回归：跑一遍闭环并打印吞吐与回溯一致性
./build/bin/adasim_headless

# 自动生成界面截图（论文配图需要可重复产出，手按截图键做不到）
./build/bin/adasim.exe --shot docs/images/main_window.png

# 算法进程：先起节点再起底座，节点会在 --wait 秒内反复重连
cd python && python run.py --wait 60
python run.py --self-test      # 不连仿真器，离线校验协议/聚类/跟踪/决策

# 点云压测：生成、光栅化、分片三段计时（结果见 7.4 与《性能压测报告》）
./build/bin/adasim_bench --iters 300
python python/bench_perception.py
```

未安装 Qt6 时，根 `CMakeLists.txt` 会自动把 `ADASIM_WITH_GUI` 置为 `OFF` 并打印告警，而不是让配置直接失败——这样"没有 Qt 也能验证核心逻辑"这条设计承诺，在构建层面同样成立。

在本机（MinGW g++ 16.1、无 Qt6）实测：配置通过，`adasim_domain`、`adasim_app`、`adasim_headless` 三个目标全部构建成功，`adasim_headless` 跑完 1500 步（30 s 仿真）输出如下特征值——单步约 0.3 µs、自车收敛到前车速度 4.00 m/s、最小 TTC 5.57 s、回溯重推演与直跑逐位一致（偏差 0）。这些数字是纯计算路径的基线，**不含渲染与通信**，因此不能直接当作端到端帧率引用。

在装有 Qt 6.12.0 的环境（Qt 自带 MinGW 13.1 工具链 + Ninja）实测：**六个目标全部构建成功**（新增 `adasim_batch` 后为七个），`adasim.exe` 启动正常，默认场景运行 2.6 s 时状态栏读数「50 FPS / 光栅化 1.02 ms / 点云 40 点」，说明渲染管线、时间轴、状态栏刷新链路在真实 Qt 环境下均可用。`adasim_headless` 在同一构建下结果一致。

需要注意编译器版本：Qt 6.12 的 mingw_64 包由 MinGW 13.1 构建，若改用系统里的 MinGW 16.1 链接会出现 C++ ABI 不匹配。配置时应显式指定 Qt 自带工具链：

```bash
cmake -S . -B build/qt -G Ninja \
  -DCMAKE_PREFIX_PATH="D:/DownLoad/Qt/6.12.0/mingw_64" \
  -DCMAKE_CXX_COMPILER="D:/DownLoad/Qt/Tools/mingw1310_64/bin/g++.exe"
```

两个进程之间的通信已由 `python/` 下的算法进程打通：TCP 分帧、UDP 分片重组、
心跳超时三条路径均有真实客户端走过，14 s 连续运行无失步、无丢片、无坏包。
接入细节与实测数据见 7.2 节。

### 7.2 算法进程的接入验证

`python/adasim_algo` 是网关的真实客户端，按「点云 → 感知 → 规划 → 控制」组织，
只用标准库，因此算法侧不需要为 numpy 预留安装步骤：

| 模块 | 职责 | 与 C++ 侧的对应关系 |
|---|---|---|
| `protocol.py` | 4 字节大端分帧、UDP 分片重组 | `TcpUdpGateway` 的镜像实现，字段与字节偏移逐一核对 |
| `perception.py` | 栅格 DBSCAN 聚类、PCA 框拟合、贪心关联、α-β 测速 | 消费 `LidarModel` 生成的点云，不读场景真值 |
| `planning.py` | CTRV 外推、IDM 跟驰、Stanley 跟踪、转向一阶滞后 | 输出 `steer / targetAccel` 交给 `PhysicsEngine` |

接入后实测（`following_lead` 场景，14 s）：

| 指标 | 数值 |
|---|---|
| 状态帧 / 指令帧 | 684 / 684（50 Hz，无丢帧） |
| 点云帧 / 平均点数 | 706 / 20.0 点 |
| 感知 + 决策单帧耗时 | 0.152 ms |
| 车距收敛 | 15.6 m → 8.0 m（IDM 平衡点理论值 7.96 m） |
| 最小 TTC / 最大加速度 | 3.07 s / 2.43 m/s² |
| 协议异常（失步/丢片/坏包） | 0 / 0 / 0 |

同一控制律在 `--truth` 模式下（跳过感知、直接用真值障碍物）最大加速度为 0.67 m/s²，
与点云链路的 2.43 m/s² 相比，差值即为感知环节引入的决策抖动——这正好构成
第五章「感知误差对闭环影响」那组对照实验的基线。

接入过程中修掉三个真实缺陷，都属于"不实测就发现不了"的类型：

1. **聚类半径不能按名义采样间距取。** 雷达沿每条边取 `int(边长/间距)` 段，
   1.9 m 车宽在 1.5 点/m 下只分成 2 段，实际点距 0.95 m 而非 0.67 m。
   eps 取 0.9 会让同一辆车的轮廓裂成两个簇；取 1.15（介于 0.95 与相邻车道
   最小边缘间距 1.6 m 之间）才同时满足"同车连通、邻道不粘连"。
2. **α-β 滤波的时间基准必须用传感器时间。** 状态帧会成簇到达，若用墙钟做 dt，
   两帧可能只差 0.2 ms，β/dt 会把厘米级残差放大成几十 m/s 的速度尖峰，
   航迹被外推到自车跟前，触发假紧急制动。改用点云自带的 `sim_time` 后消失。
3. **预测位置只能用于走廊判定，不能用于车距。** 用外推 0.6 s 的位置算车距，
   前车被凭空前推 v·0.6 ≈ 2.4 m，车距系统性高估，控制器会不自觉地跟得更近。
   实测表现为"日志 8.0 m、画面 5.6 m"的不一致。

另有一个过程性修复：命令行给的相对场景路径曾按场景目录二次拼接，
导致 `adasim scenarios/x.json` 加载失败并静默退回内置场景——已改为按
当前工作目录解析为绝对路径。

### 7.3 断线兜底：算法进程缺席时谁踩刹车

端到端联调暴露了一个设计缺口。`SimController::stepOnce()` 在
`linkAlive()` 为假时进入"断线保持模式"，把 `targetAccel` 置零而不采纳旧指令——
这个决定本身是对的（旧指令可能来自已经失联的上下文），但它等价于"匀速滑行"。
实测 `following_lead` 场景：自车以初速 8 m/s 滑行，前车 4 m/s，6 s 内车距就压到
0.00 m，物理层只是积分位姿、并不阻止穿透。

于是补了一层兜底制动，设计上有三条硬约束：

1. **只在无客户端时接管。** 算法进程一旦在线，纵向控制权完全归它。若兜底也
   参与，感知失效、决策振荡这类本该暴露的问题会被底座悄悄抹平，7.2 节那组
   "感知误差影响闭环"的对照实验就失去意义了。代码上体现为一个分支：
   `linkAlive()` 为真时只调用 `standbyGuard_.release()`，让出控制权。
2. **口径唯一。** 走廊判定与净距计算抽到领域层 `ForwardGap`
   （`nearestForwardTarget` 控制口径 / `criticalForwardTarget` 指标口径），
   `ExperimentRunner::timeToCollision` 也改为调用它。原先算 TTC 的代码里
   横向容差 2.5 m、TTC 偏移 3 m 都是散落的常量，兜底若另写一份必然分叉。
3. **控制律必须连续。** 详见下文，这一条是踩了两次坑才定下来的。

控制律分两层，输出取更狠者，中间没有"触发即满刹"的开关：

- **车距层**：目标净距取时距式 `d* = 3.0 + 1.5·v`，比例 + 阻尼
  `a = 0.35·(d − d*) − 1.0·v_rel`。车距有余量时输出为正、被夹到 0；
  逼近越急输出越负，随车距与速度连续变化。
- **硬制动层**：TTC 进到 1.2 s 以内时，改用"以现有净距刚好停住"所需的
  `−v_rel²/(2·可用净距)`，只在真要撞上时压过第一层。

最后再过一个加加速度限制（8 m/s³）：一帧之内指令不许跳变。

| 参数 | 取值 | 依据 |
|---|---|---|
| 停车净距 / 时距 | 3.0 m / 1.5 s | 时距 1.5 s 是跟驰下限，3 m 覆盖测距与制动响应误差 |
| 车距增益 / 阻尼增益 | 0.35 / 1.0 | 阶跃响应无超调，收敛约 3 s |
| 硬制动 TTC | 1.2 s | 低于此值只剩"停住"一个选项 |
| 减速度上限 | 6.0 m/s² | 与算法侧 emergency 档一致，再大超出轮胎附着 |
| 加加速度上限 | 8.0 m/s³ | 乘用车舒适性上限量级 |

控制律改了三版，每一版都是被实测数据推翻的：

1. **阈值开关（v1）**：TTC < 2.5 s 就给 −3 m/s²，否则滑行。结果成了"点刹"——
   制动使接近速度下降、TTC 回升，于是松刹、再逼近、再刹。20 s 内反复介入
   **12 次**，最小净距仍被磨到 1.97 m。教训：用"危险程度"做开关，会和
   "执行动作会改变危险程度"这件事打架，形成极限环。
2. **闩锁（v2）**：一旦介入就保持，直到接近速度 ≤ 0.05 m/s 才释放。点刹没了
   （1 次介入、稳定 8.65 m），但介入期间是恒定 −3 m/s²，退出时机也生硬，
   本质是拿"锁存"压制振荡，而不是消除振荡源。学生答辩时也解释不清为什么
   一定要锁。
3. **连续律 + 变化率限制（v3，当前）**：不再有开关，减速度是车距与接近速度的
   连续函数，再经加加速度限制落到指令上。同一场景峰值减速度从 3.0 降到
   **2.02 m/s²**、稳态净距 9.04 m、介入 1 次，且退出是斜坡而非台阶。
   振荡源被消除了，也就不需要锁存。

界面必须把这个状态显式标出来，否则用户分不清画面上的刹车来自算法还是底座：
`refreshStatus()` 在兜底介入时追加"· 兜底制动"。该状态位带 0.5 / 0.15 m/s²
的迟滞，只影响提示与计数，不影响指令——稳态时指令会在 −0.2 附近微调，
没有迟滞这个灯会闪个不停。

验证分三处（`tests/standby_guard_check.cpp` 为手工用例，未纳入 CMake，
按文件头的单行命令编译即可）：

| 验证 | 结果 |
|---|---|
| 单元用例 | 空场景/远距不介入；主场景 20 s 最小净距 9.04 m、峰值 2.02 m/s²、介入 1 次、加加速度未越 8 m/s³；20 m/s 接近静止障碍最小净距 3.10 m；对照组（去掉兜底）最小净距 −4.46 m |
| 延迟接入实测 | 底座先行 11.70 s，算法进程接入时车距 9.3 m（改前为 0.00 m），接入后最小车距 7.96 m、无 emergency |
| 在线回归 | 客户端全程在线 20 s：1000/1000 帧、最小车距 7.96 m、最小 TTC 3.04 s、兜底零介入 |

### 7.4 点云压测：十万点这条线卡在哪

开题承诺"十万点量级 P99 帧时间不超过 16.7 ms"。压测拆成生成、渲染、链路三段，
完整数据与复现命令见 **《性能压测报告》（`docs/性能压测报告.md`）**，这里只记
结论与它反过来改掉的设计。

| 环节 | 十万点实测 | 结论 |
|---|---|---|
| 生成（L3） | 0.49 ms | 占 50 Hz 步进预算 2.4%，可忽略 |
| 渲染（L4） | 720p P99 4.93 ms；1080p P99 7.74 ms | 验收线 16.7 ms，余量 3.4 倍 |
| 网络（L4） | 858 片/帧、5.95 ms、99 Mbit/s | 可用但无余量，应发送前抽稀 |
| 感知（Python） | 每点云帧 35~39 ms | **唯一不达标环节**，超节拍 2 倍 |

压测最大的产出不是这几个数，而是它逼出来的两个缺陷——两者的共同点是
**只在规模上去之后才出现，2 车 40 点的场景里永远不会暴露**：

1. **点云按物理步 50 Hz 发布。** `SimController::publish()` 原先每步发一帧点云，
   十万点下等于每秒 4.3 万个 UDP 分片、约 51 MB/s，链路被灌死。改法是把雷达
   频率从物理步里拆出来（`LidarParams::rateHz`，默认 10 Hz），状态仍按物理步
   发送。节拍用累加器而不是"每 5 步一次"：50/10 整除只是当前取值的巧合，
   换成不整除的组合，取模会固定丢掉半拍。
2. **排空 UDP 把 TCP 饿死。** 算法进程原来一次事件里"一直读到 EWOULDBLOCK"，
   十万点时接收缓冲里总有下一片在路上，于是纯 Python 侧 18 s 内状态帧 0 个、
   指令 0 条——现象是"点云收到了、车不动"。改法是单次排空上限 320 片，保证
   每轮循环都给 TCP 留出处理机会。

顺带还改了两处默认值，都属于"规模一变就现原形"的类型：

- **UDP 分片从 2000 点降到 120 点。** 2000 点一片是 24 KB，按 UDP 上限（64 KB）
  留余量没问题，但忽略了链路 MTU 1500 B：出网卡就被切成 17 个 IP 分片，丢任
  一片整包作废。120 点一片是 1464 B，恰好不超 MTU。代价是片数从 52 涨到 858、
  发送耗时从 2.5 ms 涨到 6.0 ms——这个代价换来的是"不会在真实网络上随机丢帧"。
- **点云快照改懒重建。** 渲染与点云发布各有节拍，原先每步无条件重采样，
  十万点下等于每秒白做 40 次（0.49 ms × 50）。

场景文件因此多了一个 `sensor` 块，把量程与采样密度写进场景本身：

```json
"sensor": { "lidarRange": 250.0, "lidarPointsPerMeter": 10.0 }
```

这不是为了压测方便，而是因为点云规模现在会同时改变渲染、网络与感知三处的
工作负载：**一个不能声明自身点云规模的场景文件，其性能数据是不可复现的。**

最后一条结论要写进论文，因为它最容易被追问：**十万点不是真实交通能产生的量级。**
自车 50 m 量程内每车 12.8 m 轮廓、即便 0.1 m 高密度采样也只有 130 点，凑够十万点
需要量程内 770 辆车（7,850 m² 内每 10 m² 一辆），物理上不存在。因此这条指标应
表述为"渲染与内存的上界测试"，真实车流（4 车道、150 m 量程）的工作点约 2 万点、
整帧 1.9 ms——主动说明比被追问好。

### 7.5 切入行为：把"空壳场景"变成可复现的失效工况

`cut_in_brake.json` 从第一版起就写着 `"behavior": "cut_in"` 与 `"trigger": 3.0`，
但物理层只让障碍物沿航向匀速推进，这个场景加载出来是一辆邻道车直行——
**文件存在、加载成功、什么都不发生**，属于最难排查的那类静默失败。

补实现时有两条路：把行为写进场景层（每帧新建一个"行为对象"），或写进状态。
选了后者：`BehaviorState` 挂在 `EntityState` 上，随 `WorldState` 进时间轴快照。
理由是回溯——第 300 帧快照里的那辆车，必须自带"我已经切到一半"这个事实，
否则重推演会把它当成还没开始切，结果必然与直跑不一致。这也是 2.3 节
"领域层不可有隐藏状态"的直接推论。

**横向位移用解析解而不是积分。** 设切入耗时 T、横向跨度 Δy，进度 p 处的位移取

```
ratio(p) = (1 − cos(πp)) / 2        横向速度 = Δy·(π/2T)·sin(πp)
```

端点的 sin 为零，因此横向速度在起步与收尾处都为零，航向角 `θ = asin(v_y/v)`
连续地从 0 起、回 0 止——若用恒定横向速度，起步瞬间航向会跳 6°，点云里
车身会"啪"地扭一下。解析解还有个附带好处：与步长无关，重推演必然逐位一致。

**制动从横向过半开始**，而不是等平移结束。等平移结束再刹车，两车横向已无重叠，
威胁就不存在了；真实别车正是"压进车道的同时踩刹车"。`cut_in_brake` 里
触发 2.5 s、平移 3.5 s、减速度 2.5 m/s²、减速到 1.5 m/s，正是按这个时序设的。

顺带把 `car_following` 也做实了（IDM，参数与 Python 侧一致）。它原先是枚举里的
一个名字，行为与 `constant` 完全相同——同一类沉默谎言。IDM 计算统一走
`idmAccelFor()`，参与者推进与控制用例共用一份公式，避免"场景里那辆车怎么减速"
与"我认为它应该怎么减速"两处各写一遍而分叉。

| 验证（`tests/cut_in_check.cpp`，16 项） | 结果 |
|---|---|
| 横向曲线：起止位移、中点过半、端点横向速度 | 全部为零/满足，端点斜率 2.5e-4 |
| 时序：触发前不横移、航向为零 | y 恒为 3.5 m，θ=0 |
| 平移结束贴住目标车道 | y=0.000000，θ=-0.000000 |
| 平移中航向非零（车确实是斜着切进来） | maxθ = 0.184 rad（10.6°） |
| 切入后减速到目标车速 | 9.0 → 1.50 m/s |
| 自车（IDM）最小净距 | 3.72 m，未追尾 |
| 对照组（自车不减速） | 净距 −4.50 m，追尾 → 证明场景确有威胁 |
| 切入选段重推演 | 与直跑逐位一致 |

**真实链路联调（GUI + 算法进程，12 s）**：601/601 状态与指令帧、120 点云帧、
零协议异常；最小净距 4.06 m、最小 TTC 3.65 s、峰值减速度触及 6.0 m/s² 的紧急档，
决策 follow 588 / cruise 13。切入瞬间的紧急制动是**正确行为**：邻道车以 9 m/s
压进来、净距 8.4 m 而期望净距 12 m，任何保守控制器都会先重刹再收敛。

联调还逼出一个真问题，值得记下来：**第一版场景的几何是错的**。原来前车在 30 m
处以 5 m/s 行驶，切入车 9 m/s 从 12 m 处起步，两者在 t≈4 s 时纵向几乎重合、
横向只差 2.1 m——切入车会从慢车身上"穿过去"。点云里两辆车因此并成一个簇，
算法侧表现为"目标数 2→1、目标消失、误加速"。把前车移到 45 m、提到 6 m/s 后，
几何冲突消失，目标数全程稳定为 2。

这类错误不会在单测里暴露（单测只检查那辆车自己走得对不对），也不会报错，
只会在画面里"看起来怪怪的"。**仿真平台自身的场景必须像被测系统一样被验证**，
否则基于它做的失效搜索得出的结论全是假的。

> 这条教训后来直接变成了代码：AI 模块的语义校验里加了轨迹互穿检测
> （见 7.6 节），按 0.1 s 步长外推所有参与者做包围盒检查，
> 自检里有一条用例专门复现上面这个 bug。

### 7.6 AI 增强模块：语言生成与失效搜索的接入

模块的完整设计见 `docs/AI增强模块设计.md`，这里只记与**架构**有关的部分。

**接入方式**：`ai/` 是独立进程，与底座之间只有两份契约——场景文件（JSON）
和指标（行式 JSON）。为此新增第七个目标 `adasim_batch`，常驻读 stdin、
写 stdout，每次评估 0.4 ms。删除整个 `ai/` 目录，C++ 工程仍可正常构建，
这条性质在重构中被反复验证。

**三处必须回到 C++ 侧才能补的缺口**，都不是 AI 模块自己能解决的：

| 缺口 | 后果 | 修法 |
|---|---|---|
| `PhysicsEngine::step` 不读 `friction` | "路面湿滑"这个搜索变量的效果恒等于零 | `WorldState` 携带 `friction`，加速度下界取 `-μ·g`；参与者制动同样封顶 |
| `ExperimentRunner` 只会滑行 | 自车对任何场景都只有一种反应，目标函数近似常数 | 新增 `EvaluationConfig`，闭环时自车按 `idmAccelFor` 跟驰 |
| 行为枚举没有"制动" | "前车突然急刹"这句话无处落地，只能退化成"前方有静止车" | 新增 `BehaviorKind::Brake` |

第一条最值得说：它是**沉默的失效**。搜索照常收敛、报告照常出数字，
但其中一个维度是假的。验证方法是固定其余参数只改 μ，看峰值减速度是否
等于 μ·g——实测 0.6→5.89、0.3→2.94、0.15→1.47，全部吻合。

**为什么评估服务不走既有 TCP 网关**：那是实时链路的通道，心跳与帧率语义
都为在线仿真设计。离线评估是"请求—应答"式短事务，行式管道更贴切，
也不会让 AI 进程误以为自己在跟一台正在跑的仿真器说话。这条边界与
"AI 不进入实时链路"是同一件事的两面。

**实测**（`preset_cut_in_brake`，预算 100 次）：

| 方法 | 最优严重度 | 碰撞样本 |
|---|---:|---:|
| 贝叶斯优化 | 1.1633 | 47 / 100 |
| 随机搜索 | 1.1105 | 6 / 100 |
| 基线（模板原值） | 0.2645 | 0 |

碰撞命中率 47% 对 6%，比"最优值高 0.05"更能说明问题：贝叶斯把预算集中到了
失效边界附近。生成器侧另有 108 项离线自检（`python ai/selftest.py`），
不需要网络、不需要密钥，可作为回归基线。

### 7.7 五组实验带出的三处接口补充

做完五组实验后回补了三处**流经全链路**的字段。它们的共同点是：缺了它，
实验结论要么测不出来，要么测出来的是别的东西。

| 补充 | 位置 | 为什么必须走全链路 |
|---|---|---|
| `curvature` | `ScenarioTemplate` → `WorldState` → `StatePacket` → 状态 JSON → `StateFrame` | 算法侧要按曲率生成参考路径。若只在模板里存着，`curvature` 就是第二个"只解析不生效"的字段（第一个是 `friction`），弯道场景会退化成直道，而横向误差仍然是 0——看起来完美，实际什么也没测 |
| `egoPose` | `ScenarioTemplate` → `ScenarioService::buildInitialState` | 自车若永远从参考线正中起步，直道横向误差恒为 0。给 0.3 m 初始偏置后，同一场景的横向 RMS 才有 0.038 m 这个有意义的数 |
| `ackSeq` | `TcpUdpGateway::publishState`（网关内部，不进领域层） | 测往返时延需要"指令被消费"的证据。让底座把最近消费的 `seq` 回带，两端各用自己的单调时钟，绕开跨进程时钟对齐 |

`ackSeq` 特意没有进 `StatePacket`：它不是仿真状态的语义，只是网关的观测
辅助，放进领域结构会让领域层知道"有人在测时延"。这与 `lastRoundTripMs()`
那类死字段的教训一致——**测不到的数不要假装有接口**。

配套的实验脚本（`tools/run_experiments.py`、`tools/eval_scenario_gen.py`）
也放在仓库里：实验必须能原样重跑，否则"数据可复现"只是口号。
数据与口径见 `docs/实验报告.md`。

## 8 分层的代价

任何结构都有成本，写进论文比藏着更可信。

**其一，跨层数据拷贝。** 50 Hz × 200 个实体，若每帧深拷贝一份快照，拷贝开销会挤占物理步进的预算。本设计的对策是共享只读快照（`shared_ptr<const WorldSnapshot>`）加对象池，快照只在完整快照帧分配，增量帧复用。

**其二，调用链变长。** 一次回溯要穿过 L1→L2→L3→端口，断点调试时栈更深。对策是端口数量控制在五个以内，且装配根集中，出问题先看 `main.cpp` 的连接关系。

**其三，性能热点不宜过度分层。** 渲染管线内部的批构建、体素降采样、空间索引剔除属于同一变化源（都在"如何把点画出来"这一件事上），不应再拆成三层接口互调——那会引入虚函数调用与内联失败，把 8 ms 的单帧预算吃掉。**分层的边界应画在变化原因不同的地方，而不是画在代码行数均匀的地方。** 这是本设计最重要的一条取舍。

## 10 待定与后续

以下几点需要在实现阶段确认，暂不作为结论：

1. 渲染线程是否真的独立于 GUI 线程。当前按"离屏光栅化 + GUI 贴图"设计，若实测贴图开销可忽略则合并回 GUI 线程，可少一次上下文切换。
2. 快照的内存分配策略（对象池 vs 定长环形）需按实测的分配耗时决定。
3. ~~`ExperimentRunner` 与 AI 进程的失效搜索职责边界~~：已落地为 `adasim_batch` 常驻进程 + 行式 JSON，见 7.6 节。

压测（7.4）之后新增三条，都已定位但尚未实施，按性价比排序：

4. **感知向量化。** 纯 Python 在 2 万点上是 35~39 ms，是当前唯一不达标的环节。
   把聚类与 PCA 搬到 numpy 预计可进 5 ms，届时 `MAX_POINTS` 抽稀可以取消。
5. **发送前体素抽稀。** 十万点直接上线要 858 片/帧，抽稀到 2~3 万点可把链路开销
   降到 1/4，且体素保形优于当前按索引等步长的抽样。
6. **点云压缩。** 帧间增量或量化到 16 位，可再省一半带宽；优先级低于前两项。
