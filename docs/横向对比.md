# 横向对比：ADASim 与主流自动驾驶仿真平台

对应开题报告"预期成果（3）"与 §6 实验设计第（5）项：在可比维度上与 CARLA、SUMO、
PreScan 等平台做横向对照，界定本平台的能力边界与适用场景。

**这份文档不排序。** 六个平台的定位不同，把"谁更强"压成一个分数没有意义；
有意义的是把"每一项能力在哪个平台上能做到什么程度"摆清楚，然后说明 ADASim
在哪一格够用、在哪一格明确不够用。

### 1.1 三条能力分界线

从表 1 能划出三条线，ADASim 的位置由这三条线决定：

**（1）感知保真度：CARLA/PreScan ≫ ADASim ≫ SUMO/CommonRoad（无传感器）。**
ADASim 的点云是**障碍物轮廓的等距采样**，不是射线求交，没有遮挡、多径、
反射率与运动畸变。它能支撑"目标在不在、聚成几个簇、框拟合准不准"，
不能支撑"感知算法的检测率与虚警率"。这条线必须写清楚，否则容易被误用。

**（2）行为复杂度：SUMO ≫ CARLA ≈ PreScan > ADASim ≈ highway-env。**
SUMO 的路口冲突、信号配时、路径重规划是二十年积累，ADASim 只有 4 类模板。
这是当前最实的短板：E5 的场景生成里有 24% 的描述落到"路口冲突/施工绕行"
只能回退到最接近的模板（见 `docs/实验报告.md` §5）。

**（3）闭环可观测性：ADASim 与其余平台是不同的问题。**
其余平台回答"我的算法在场景里表现如何"，ADASim 额外回答"这条链路本身
健康吗"——往返时延、帧龄、断链后的兜底行为、回看到第 N 帧时点云长什么样。
后一组问题在 CARLA 里要靠外部脚本自己埋点，ADASim 把它做成了产品功能
（HUD + `--metrics` + 帧级时间轴）。

## 2. 部署门槛

开题报告 §6（5）要求的正是这一张表。**冷启动**定义为"从进程入口到首帧
贴到界面上"，不是"进程起来了"——后者会漏掉 Qt 平台初始化、场景加载与
首帧光栅化，在 Windows 上就是几百毫秒。

ADASim 的冷启动由程序自己打点（`MainWindow::firstFrameReady`），
基线平台用外部计时包住"启动到第一次 `render`/`step`"。

### 表 2 部署门槛

| 平台 | 安装方式 | 磁盘占用 | 冷启动到首帧/首个 step | 最低硬件 | 部署步骤 |
| --- | --- | --- | --- | --- | --- |
| CARLA 0.9.15 | 下载预编译包解压 + pip 装 client | **约 20 GB**（**文档**） | 未实测（需 ≥8 GB 显存，本机为集显） | NVIDIA 2070 同级、≥8 GB 显存、Win10/11 或 Ubuntu 20.04/22.04（**文档**） | 解压 → 装 client → 起 server → 跑脚本 |
| SUMO 1.28.0 | msi 安装包 / zip 免安装 / apt | 安装包 **166 MiB**（**实测**下载字节） | 未实测 | 无 GPU 要求 | 安装 → 设 `SUMO_HOME` → 跑 `sumo-gui` |
| PreScan | 商业授权安装（需 MATLAB/Simulink） | 未公开口径 | 未实测 | Windows + MATLAB + 授权 | 装主程序 → 装 MATLAB → 配 license → 建工程 |
| highway-env 1.12.1 | `pip install highway-env` | **248 MB**（含依赖，**实测**） | **2362 ms**（5 次中位，**实测**） | 无 GPU 要求 | 1 条命令 |
| CommonRoad（commonroad-io） | `pip install commonroad-io` | **321 MB**（含依赖，**实测**） | **1186 ms**（5 次中位，**实测**） | 无 GPU 要求 | 1 条命令 |
| **ADASim** | 源码 CMake 构建 | **39 MB**（含 Qt6 运行库的部署目录，**实测**）；自身二进制 **0.47 MB**；源码 358 KB | **293 ms**（5 次 252–307 ms，**实测**） | 任意 x86-64 + 集显；无 Qt 的 `adasim_headless` 只需编译器 | 装 Qt6 → `cmake -S . -B build` → `cmake --build build` → 运行 |

### 2.1 轻量基线的实测口径

两个 pip 基线装在独立 venv（`python -m venv`）里，只装各自声明的依赖，
体积取 `site-packages` 的磁盘占用，启动时间取"解释器冷启动 + import +
创建环境 + 首个 `reset()`"，各跑 5 次取中位数。

<!-- MEASURED_PIP_TABLE -->
| 平台 | 安装后 `site-packages` | 冷启动（进程入口→首个 step/首帧） | 其中 import | 首个场景/环境 |
| --- | ---: | --- | ---: | --- |
| highway-env 1.12.1 | **248 MB** | **2362 ms**（5 次 2306–4775） | 1481 ms | `highway-v0` 建环境 + `reset` + `step`：220 ms |
| CommonRoad（commonroad-io 2026.1） | **321 MB** | **1186 ms**（5 次 1168–1217） | 646 ms | 建 4 lanelet 场景 + 写 XML + 读回：6 ms |
| **ADASim** | **39 MB**（含 Qt6 运行库）/ 自身 0.47 MB | **293 ms**（5 次 252–307） | — | 载入场景 + 首帧光栅化已含在内；无 Qt 的 `adasim_headless` 跑完 1500 步只要 **126 ms** |

两个 pip 基线的轮子本身很小（highway-env 111 KB、commonroad-io 2.31 MB），
装完之后却是 248 MB 与 321 MB——**体积全在依赖上**（numpy、pandas、scipy、
matplotlib、shapely、lxml）。这一点值得单列出来，因为它推翻了"pip 装的一定
比编译出来的 Qt 程序轻"这个直觉：在本机，ADASim 的 39 MB 比两个"轻量基线"
小一个数量级。

冷启动的排序也是反直觉的：两个 Python 基线分别 2.4 s 与 1.2 s，比 ADASim 的
293 ms 慢 4 倍和 8 倍，主要开销是解释器与 numpy/scipy 的导入，而不是场景本身
（CommonRoad 真正的场景往返只要 6 ms）。这解释了为什么本平台把"能在
`ctest` 里 1.35 s 跑完 7 个用例"当成设计目标之一：算法回归要能进 CI，
启动开销必须压在百毫秒量级。

**这张表要说明的一件事**：ADASim 的 39 MB 里，Qt6 运行库占 38.5 MB，
自身代码不到 0.5 MB。也就是说"部署体积"这一项它不是靠写得省赢的，
而是靠**不依赖 3D 引擎与游戏资产**——CARLA 的 20 GB 里绝大部分是地图与
车辆资产，那些东西换来的正是 ADASim 明确放弃的感知保真度。

## 3. 性能可比维度

只有 ADASim 有本机实测；其余平台列出"若要做同一项对比需要什么条件"，
不做数字断言。这一节的作用是**给后续工作留接口**，不是给结论。

### 表 3 性能维度的可比性

| 维度 | ADASim（实测） | 其他平台的可比条件 |
| --- | --- | --- |
| 十万点渲染帧时间 | 1280×720：中位 4.12 / P99 **5.99 ms**（等效 210 FPS）；1920×1080：P99 **11.27 ms**（111 FPS） | CARLA/PreScan 需在同类 GPU 上跑同规模点云，且要区分"传感器仿真耗时"与"画面渲染耗时"——两者在他们的架构里是同一件事，在 ADASim 里是分开的（算绘分离） |
| 控制回路往返时延 | 轻载 RTT 均值 **19.99 ms**、净时延 **<1 ms**；十万点感知链路净时延 88.5 ms（瓶颈在 Python 逐点重组，见 §4） | 需平台提供"指令发出→被消费"的时间戳回带。CARLA 的 client-server 是 RPC，语义不同（调用返回即完成），不能直接比 |
| 回溯一致性 | 20 步重推演位姿偏差 **0.000e+00**，单次回溯 0.009 ms | 需平台提供"回退到第 N 帧并重推演"的接口。CARLA recorder 是回放录像（不再计算），SUMO 无回退语义，均不等价 |
| 场景生成有效性 | 50 条自然语言描述：结构合法 100%、语义匹配 96%、可加载 100%、模板回退 24% | 无同类能力可直接对照（CARLA 的 `scenario_runner` 是手写 XML 场景，不含生成） |

## 4. 结论：定位、边界与后续

### 4.1 适用

1. **算法闭环回归**：一次 `ctest` 1.35 s 跑完 7 个用例，含跟驰、切入、断链、
   注入四类不变量。这个量级才能进 CI；CARLA 起一个 server 就要几十秒。
2. **通信与兜底策略验证**：双通道（TCP 状态/指令 + UDP 点云）让"时延"和
   "丢包"成为可测量、可注入的量，断链后的兜底制动有独立判据（`standby` 与
   `link` 分列），这是本平台区别于其他平台的核心能力。
3. **教学与答辩演示**：无 GPU、293 ms 起画面、右键注障即时见效，在普通
   学生笔记本上就能演示"感知→决策→控制"整条链路，包括它失效时的样子。

### 4.2 不适用（明确写出来，避免误用）

1. **感知算法的精度评估**。点云是轮廓采样，没有遮挡与反射特性；用它算
   检测率/虚警率得到的数字没有外部效度。要做这件事必须换 CARLA/PreScan。
2. **整车动力学与乘坐舒适性标定**。运动学自行车模型不含轮胎侧偏、载荷转移、
   悬架，横向加速度超过约 4 m/s² 后与实车偏差不可忽略。
3. **复杂路口与大规模交通流**。行为只有 4 类模板，路口冲突尚未建模
   （E5 中 24% 的描述因此回退），路网是一维的，不支持任意拓扑。

### 4.3 后续优先级（按"补哪个短板收益最大"排）

| 优先级 | 事项 | 理由 |
| --- | --- | --- |
| 高 | 感知链路 Python 侧向量化（十万点净时延 88.5 ms → 目标 <10 ms） | 当前唯一不达标项；且是"能不能上十万点规模"的门槛 |
| 高 | 行为模板补到 8 类，含路口冲突与施工绕行 | 直接消掉 E5 的 24% 回退率 |
| 中 | 弯道参与者沿参考线推进（当前各按自身航向直线走） | 弯道场景的可信度问题，不影响直道实验结论 |
| 低 | 3D 视角与相机模型 | 与"轻量、可在集显上跑"的定位冲突，除演示需要外不做 |

## 5. 复现

```bash
# ADASim 冷启动（程序内打点，5 次取范围）
build/qt/bin/adasim.exe scenarios/following_lead.json --shot out.png --shot-delay 200

# ADASim 部署体积（windeployqt 后的可发行目录）
windeployqt --release --no-translations build/qt/bin/adasim.exe && du -sh <部署目录>

# ADASim 十万点帧时间 / 时延 / 回溯
build/qt/bin/adasim_bench.exe --no-udp
python tools/run_experiments.py --group e2
build/verify/replay_check.exe

# 基线平台（独立 venv，避免污染主环境）
python -m venv /tmp/venv_hw && /tmp/venv_hw/Scripts/pip install highway-env
python -m venv /tmp/venv_cr && /tmp/venv_cr/Scripts/pip install commonroad-io
```
