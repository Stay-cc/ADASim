# AI 增强模块设计

本文覆盖开题报告 5.3.7 节承诺的两个功能：**语言驱动的场景生成**与
**贝叶斯失效搜索**。两部分共用同一份参数化场景模板的定义，因此
"描述—生成—搜索"是一条链路，而不是两个互不相干的工具。

模块以独立进程实现，与 C++ 底座之间只有两份契约：**场景文件（JSON）**
与**指标（行式 JSON）**。它不出现在实时链路里——这是刻意的，理由见第 6 节。

---

## 1 模块边界

| 关注点 | 归属 |
|---|---|
| 场景模板的结构与语义约束 | `ai/adasim_ai/schema.py`、`validate.py` |
| 自然语言 → 模板 | `ai/adasim_ai/nlu.py`、`generate.py` |
| 参数空间搜索 | `ai/adasim_ai/gp.py`、`search.py` |
| 单次仿真与指标 | C++ `adasim_batch`（复用 `ExperimentRunner`） |
| 实时仿真、渲染、通信 | C++ 底座（不受本模块影响） |

依赖方向是单向的：AI 模块调用底座，底座完全不知道 AI 模块的存在。
删除整个 `ai/` 目录，C++ 工程仍可正常构建运行（已验证）。

**零第三方依赖**。解析、校验、高斯过程、期望改进全部用标准库实现，
理由与 `python/` 侧一致：毕设环境不该因为装不上某个包就跑不起来。
代价是数值代码得自己写、自己验（见 5.1 节的自检）。

## 2 场景模板：唯一的结构真相

`ai/adasim_ai/schema.py` 里的 Schema 被三个地方派生使用：

1. 结构校验器（`check_structure`）；
2. 喂给语言模型的字段说明（`describe_for_prompt`）；
3. 回退时判断预置模板缺哪些字段。

各写一份的后果是：模型按提示词产出 A，校验器按 Schema 拒绝 A，
回退模板又补了第三套字段——出问题时根本分不清哪一环错了。

字段与 C++ `ScenarioTemplate` 逐一对齐，Python 侧不做"更 Pythonic"的
改造（比如把 `x/y/theta` 收进 `pose` 子对象）。两侧要读写同一批文件，
任何形态差异都会变成一类只在跨语言时暴露的 bug。

### 2.1 为语言表达而新增的行为

做自然语言解析时发现一个硬缺口：**"前车突然急刹"这句话无处落地**。
领域层的 `BehaviorKind` 只有匀速、跟驰、切入三种，把前车设成静止表达的是
"前方有静止障碍"——那是另一个场景：前者自车一上路就看见它，后者要到
制动发生才构成威胁。

于是补了 `Brake` 行为（到触发时刻起以 `brakeAccel` 减速至 `speedFloor`）。
这与上一轮把 `car_following` 从"枚举里的一个名字"做成真 IDM 是同一类修正：
**语言能表达的东西，平台必须能承载**，否则解析器只能默默删掉用户意图，
而用户看到的是一个"看着像、跑起来不对"的场景。

同一轮还补了 `egoSpeed` 字段。此前自车初速只能从 `parameters` 里找一个叫
`ego_speed` 的项、取它的 `min` 当基线——搜索下界和实际取值绑成同一个数，
改一个必伤另一个。现在它是模板的一等字段，`egoSpeedExplicit` 标志保证
旧场景文件的语义不变。

## 3 自然语言生成

### 3.1 两条通路，规则解析是基线而非备胎

| | 规则解析 | 语言模型 |
|---|---|---|
| 确定性 | 是（同一句话十次一样） | 否（跨版本不保证稳定） |
| 依赖 | 无 | 端点 + 密钥 |
| 覆盖 | 有限（关键词 + 单位表达式） | 开放 |
| 用途 | 回归基线、离线可用、与模型输出对照 | 处理规则覆盖不到的表述 |

把规则解析当"没网时的备胎"，就会写得敷衍，最后只在演示时露一次面。
这里把它当主角之一：它是唯一能进单元测试的通路，也是判断"这句话有没有
歧义"的参照——两条通路给出不同**意图**时，说明原话本身含糊，值得人看一眼
（`_note_rule_divergence`）。

### 3.2 三级降级链

```
① 语言模型   结构错 → 回填错误重试一次 → 仍失败则放弃此路
② 规则解析   槽位足够即采信（意图明确 或 给了关键数值）
③ 预置模板   挑最像的一张做骨架，叠加能从原话确认的字段
```

**只有结构错才重试。** 语义错（前车在自车后头、两车初始重叠）通常是模型
对物理世界的理解出了问题，重试十次还是错，只是白花时间和 token；这类错误
直接交给下游标注、由人确认。

**第 ③ 级不是"随便给个默认场景"。** 若回退到一张无关模板，用户看到的是
"系统假装成功了"，比明确报错更坏。因此按槽位距离挑最像的一张，并把
"哪些字段来自原话、哪些是模板带的"逐条标出来：

```
通路     : preset（模板：前车紧急制动）
待确认字段: /egoSpeed、/friction
说明     : 以下字段原话未提及，沿用模板取值
```

距离度量用固定权重（意图不一致 +10、车道数不一致 +1、速度相对差按比例）。
权重是手工调的，但依据可解释：意图错一次场景就完全不是那个场景了，
速度错一点还能用。与其用一套"更优雅"的自动度量，不如把这种领域常识写死在代码里。

### 3.3 校验分两层，因为处置方式不同

| | 结构校验 | 语义校验 |
|---|---|---|
| 查什么 | 类型、必填、取值范围、枚举 | 物理是否讲得通 |
| 典型错误 | `x` 写成字符串、缺 `actors` | 前车在自车后方、两车初始重叠 |
| 处置 | 回填给模型重试 | 拦截并转人工 |

语义校验里最值钱的一条是**轨迹互穿检测**。上一轮做切入场景时踩过：
前车 30 m/5 m/s、切入车 12 m/9 m/s，两者在 t≈4 s 纵向重合而横向只差
2.1 m，切入车直接从慢车身上穿过去。单测只检查"那辆车自己走得对不对"，
查不出来；加载也不报错；只在画面里看着别扭。而基于这种场景做失效搜索，
结论全是假的。

现在校验器按 0.1 s 步长外推所有参与者的轨迹，做轴对齐包围盒互穿检查。
运动学假设与 C++ `cutInLateralRatio` 逐字对应——两处若不一致，校验会说
"不重叠"而仿真里撞上，这是校验器最不能出的错。自检里有一条用例专门
复现那个 bug，必须被抓出来。

## 4 失效搜索

### 4.1 问题形式

| 项 | 内容 |
|---|---|
| 搜索变量 | 自车初速、初始跟车间距、切入时刻、附着系数、感知噪声 |
| 区间 | 取自场景 `parameters` 块，未声明的变量不搜索 |
| 评估 | 跑一遍闭环仿真，取是否碰撞、最小 TTC、最小净距、撞击速度、峰值加速度 |
| 目标 | 最大化失效严重度 `severity(x)` |
| 预算 | ≤100 次评估 |

### 4.2 目标函数的构造

```
collided  → 1.0 + 0.5 · clamp(impactSpeed / 10, 0, 1)   ∈ [1.0, 1.5]
未碰撞    → 1 / (1 + max(minTtc, 0))                    ∈ (0, 1]
```

两段在 TTC→0 处都取值 1.0，因此**连续**。这一点很重要：不连续的目标会让
GP 在跳变处拟合出一条陡坡，采集函数被它带偏，把预算全花在跳变点两侧。

碰撞深度用"撞击时的接近速度"而不是"穿透深度"，是踩坑改出来的：
最初用穿透深度，实现时发现碰撞后立即终止仿真（省预算），穿透深度永远
只是刚接触那一帧的值，在碰撞区间里退化成常数——搜索器在那里拿不到任何
梯度，后半程等于随机游走。实测改前最优严重度 1.0103，改后 1.1633。

**加速度不进目标函数。** 它与失效程度不同向：一次平稳的紧急制动可以有
6 m/s²，一次轻微剐蹭可能只有 2 m/s²。塞进同一个标量会引入矛盾信号。
按开题约定，它作为报告指标随结果输出，不参与优化。

### 4.3 闭环评估与感知噪声

`ExperimentRunner` 原本是**纯滑行**（`targetAccel = 0`）。用它做失效搜索
毫无意义——自车对任何场景都只有一种反应（撞上去），目标函数在参数空间里
几乎是常数，"搜索"退化成随机抽样。

新增 `EvaluationConfig`，`closedLoop=true` 时自车按 IDM 跟驰。IDM 用的是
`domain::idmAccelFor` 的标量版本——与场景里那些参与者**同一套公式与参数**。
自车与参与者各用一套纵向律的话，搜索得到的"临界间距"只对其中一套成立，
结论无法迁移。

感知噪声只污染控制器的输入，不污染指标计算：

```cpp
gapObs = gap.bumperGap + noise * pseudoGauss(seed, step);
cmd.targetAccel = idmAccelFor(v, cruise, gap.valid, gapObs, leadSpeedObs);
```

否则噪声会直接算进 TTC，测出来的是"噪声"而不是"系统失效"。

噪声用 `(seed, step)` 直接算出，而不是维护一个 RNG 对象：后者会让
"优化器恰好问过多少次"影响结果，同一组参数重跑就对不上，
GP 拟合的就成了噪声本身。

### 4.4 让 `friction` 真正生效（本轮最关键的修复）

原实现里 `PhysicsEngine::step` **根本不读 friction**——它只是模板里的一个
数字，物理层从未使用。于是"路面湿滑"这个搜索变量无论怎么变，仿真结果
都一模一样。这类问题最危险：搜索照常收敛、报告照常有数字，但其中一个
维度是假的。

修复分三处：

1. `WorldState` 新增 `friction` 字段。放进状态而不是引擎成员变量，
   因为回溯重推演时它必须跟着帧一起回退。
2. 自车纵向加速度下界改为 `-max(accelMin, -μ·g)`。
3. 参与者的制动（`brake` 与 `cut_in`）同样受 `μ·g` 封顶——否则会出现
   "前车刹得住、自车也刹得住"的假象。

验证（自车 20 m/s 冲向 30 m 静止车）：

| 附着系数 μ | 峰值减速度 (m/s²) | μ·g |
|---:|---:|---:|
| 0.90 | 6.00 | 8.83（受车辆极限 6.0 约束） |
| 0.60 | 5.89 | 5.89 |
| 0.30 | 2.94 | 2.94 |
| 0.15 | 1.47 | 1.47 |

μ ≤ 0.6 时峰值减速度严格等于 μ·g，说明附着约束真的在起作用。

### 4.5 高斯过程与期望改进

核函数选 Matérn 5/2 而不是 RBF：失效边界通常是"折线"而不是光滑曲面
（间距略大就安全、略小就撞），RBF 假设的二阶可导会在边界附近过度平滑，
把真正的拐点抹掉。

两处数值细节值得记：

- **用 Cholesky 分解而不是求逆**：`K⁻¹` 的条件数会平方级恶化，n=100 时
  直接求逆已能看出明显的数值漂移。
- **预测方差出现负数时夹到 0**：这是浮点误差，不是物理。留着它，
  期望改进里的 `sqrt(σ²)` 会变成 NaN，整片采集函数失效。

超参数（长度尺度）在候选集上用对数边际似然选，但**只在初始化完成后选一次**。
每轮重选让开销变成 7 倍（候选长度有 7 个，每个都要做一次 O(n³) 的 Cholesky）：
实测 100 次预算下每轮重选要 55 s，选一次只要 24 s（含两种方法各跑一遍）。
而且数据量小时 MLE 本身的估计噪声就大，反复重选会让模型在几组超参之间跳来跳去。

采集函数在"700 个全局随机候选 + 已评估点邻域扰动"里取 EI 最大者。
只撒全局点会浪费预算，只做局部扰动又可能卡在局部最优。

### 5.3 失效搜索对照（`preset_cut_in_brake`，预算 100）

| 方法 | 最优严重度 | 碰撞样本 | 评估次数 |
|---|---:|---:|---:|
| 贝叶斯优化 | **1.1633** | **47 / 100** | 101 |
| 随机搜索 | 1.1105 | 6 / 100 | 101 |
| 基线（模板原值） | 0.2645 | 0 | — |

**碰撞命中率 47% 对 6%**——这是比"最优值高 0.05"更硬的证据：贝叶斯把预算
集中到了失效边界附近，而随机采样在 5 维空间里几乎全落在"恒安全"或
"恒碰撞"的平原上。

最优解：自车 16 m/s（区间上界）、切入时刻 1.01 s（几乎是立刻就切）、
前车间距 60 m（给自车留足加速空间）、附着 0.84、感知噪声 0.135。
物理上说得通：**高速 + 极早切入 + 长加速距离**，自车在切入发生时已经没有
制动余地。撞击速度 3.27 m/s，最小净距 −2.27 m。

评估开销：单次仿真 0.40 ms，101 次全程 41 ms。GP 拟合与采集函数是主要
耗时（约 20 s），仿真反而可以忽略——这恰好说明"评估昂贵"这个假设在本
平台上是保守的，100 次预算完全放得开。

## 6 为什么必须隔离于实时链路

场景生成与失效搜索都可能耗时数百毫秒以上（前者等模型响应，后者要跑几十次
仿真）。把它们放进主循环，十万点量级下的帧率指标立刻失真。

因此：

- 场景生成只在**编辑态**触发，此时仿真尚未启动；
- 失效搜索只在**批量离线模式**下运行，由外部脚本按队列提交；
- 主循环内部不存在任何对模型的同步等待。

这条约束也决定了两侧的接口形态——底座向模块暴露的是"加载场景"与
"跑完取指标"两个原子操作，而不是逐帧回调。

### 6.1 批量评估服务协议

`adasim_batch` 是常驻进程，stdin/stdout 行式 JSON：

```json
{"path": "ai/out/_eval_tmp.json", "noise": 0.4, "seed": 1, "closedLoop": true}
{"collided": false, "minTtc": 2.25, "minGap": 1.96, "maxAbsAccel": 6.0,
 "impactSpeed": 0.0, "travelled": 23.5, "steps": 1000, "wallMs": 0.32, "ok": true}
```

三个设计决定：

1. **不用既有 TCP 网关。** 那是实时链路的通道，心跳与帧率语义都为在线
   仿真设计。离线评估是"请求—应答"式短事务，行式管道更贴切，也不会让
   AI 进程误以为自己在跟一台正在跑的仿真器说话。
2. **常驻而不是每次起进程。** 一次评估约 0.4 ms，而进程启动 + Qt 初始化
   要 100 ms 以上。100 次评估若每次都起进程，光启动就 10 s 起步，
   "100 次预算"这个前提就失去意义了。
3. **场景走文件而不是内联进请求。** 好处是每一轮跑了什么都有据可查，
   事后能把"第 37 次评估为什么撞了"原样复现。写在内存里就只能重跑整个搜索。

## 7 已知限制

1. **规则解析的关键词表是有限的。** 当前覆盖切入、急刹、行人、静止障碍、
   湿滑、弯道、车道数、速度、距离、触发时刻。超出这些表述就得靠模型，
   或回退到预置模板。扩充关键词是持续的活，不是一次能做完的。
2. **`lead_gap` 在切入场景里是间接变量。** 它绑定的是同车道前车的纵向位置，
   而切入车的位置固定在 12 m。前车挪远只是给自车留出更多加速空间，
   所以它通过"加速距离"间接影响严重度，而不是直接决定碰撞。这点容易误读，
   在报告里表现为该变量总取区间上界。
3. **GP 是单目标标量模型。** 多目标（如"碰撞概率 vs 制动舒适性"的
   帕累托前沿）需要 EHVI 一类的方法，不在本轮范围内。当前用加权标量近似，
   并把三项原始指标全部报告出来供人工判断。
4. **未做感知链路闭环。** 搜索用的是"距离观测加高斯噪声"的抽象模型，
   没有把点云过一遍真实感知。理由是：那样单次评估会从 0.4 ms 涨到 35 ms
   （纯 Python 感知 2 万点耗时），预算内能评估的次数掉两个数量级。
   抽象模型适合"找边界"，真实感知适合"验证边界上的具体点"——
   后者留给实验章节挑几个最危险工况做定点验证。
