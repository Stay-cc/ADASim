# ADASim 性能压测报告

> 对象：点云链路的规模上限——十万点能否实时
> 日期：2026-11-23　　代码版本：git `3aac744` 之后的点云压测分支
> 复现命令见 §2，原始输出可从 `adasim_bench` 与 `bench_perception.py` 直接重跑

## 1 要回答的问题

开题报告里写下的验收口径是："十万点量级平均帧率不低于 60 FPS，P99 帧时间不超过
16.7 ms"（§4.5 实验设计）。这句话必须拆成三个可测的子问题，否则无法验证：

1. **生成**：一帧十万点，仿真侧要做多少计算？
2. **渲染**：把十万点画到 1280×720 要多久，余量够不够 60 FPS？
3. **链路**：十万点按 10 Hz 上线，网络与算法进程扛不扛得住？

前两个是纯计算，可以用基准程序反复测；第三个只有在真实双进程闭环里才测得准，
也因此暴露了两个此前从未出现的问题（§5）。

## 2 方法与可复现性

| 环节 | 工具 | 命令 |
|---|---|---|
| 生成 + 渲染 + 分片 | `adasim_bench` | `adasim_bench --iters 120` |
| 感知 | `python/bench_perception.py` | `python python/bench_perception.py` |
| 端到端 | GUI + 算法进程 | `adasim scenarios/stress_dense.json --shot ... --shot-delay 18000` 与 `python run.py --duration 16` |

压测场景由 `tools/gen_dense_scenario.py` 生成，参数在文件里显式声明：

```json
"sensor": { "lidarRange": 250.0, "lidarPointsPerMeter": 10.0 }
```

十万点 = 792 辆车 × 每车 130 个轮廓点。**这个数量级不是正常交通能产生的**，
理由见 §4.1，所以它是合成载荷，而不是"某个真实工况"。

计时口径：每个档位预热一次后连续采 300 次，报中位数、p95 与 p99。取中位数是因为
Windows 上偶发的调度抖动会把均值拉高 20% 以上；报 p99 是因为开题承诺的验收指标是
"P99 帧时间不超过 16.7 ms"，只看平均值说服力不足。同一档位重复运行的波动约 ±5%。

测试机：Windows 11，MinGW 13.1 编译，Qt 6.12，单线程 CPU 软件光栅化（未启用 GPU）。

## 3 结果

### 3.1 生成与渲染（1280×720，0.1 m/px）

| 车数 | 采样密度 | 点数 | 点云生成 中位/p95 | 整帧 中位/p95/p99 | 其中点云段 | P99 达标 |
|---:|---:|---:|---:|---:|---:|:--:|
| 2 | 1.5 点/米 | 40 | 0.000 / 0.000 ms | 0.331 / 0.517 / 0.643 ms | 0.000 ms | ✓ |
| 2 | 10 点/米 | 260 | 0.001 / 0.001 ms | 0.496 / 0.616 / 0.852 ms | 0.002 ms | ✓ |
| 192 | 5 点/米 | 1.3 万 | 0.066 / 0.070 ms | 1.557 / 1.910 / 2.142 ms | 0.056 ms | ✓ |
| 384 | 10 点/米 | 5.0 万 | 0.238 / 0.279 ms | 2.919 / 3.404 / 3.879 ms | 0.238 ms | ✓ |
| **792** | **10 点/米** | **10.3 万** | **0.485 / 0.613 ms** | **4.218 / 4.712 / 4.929 ms** | **0.419 ms** | **✓** |
| 792 | 20 点/米 | 20.4 万 | 0.930 / 1.182 ms | 4.513 / 5.011 / 5.294 ms | 0.751 ms | ✓ |
| 792 | 40 点/米 | 40.7 万 | 1.812 / 2.139 ms | 5.190 / 5.610 / 5.958 ms | 1.312 ms | ✓ |

按开题承诺的验收线（十万点、P99 ≤ 16.7 ms）：**实测 P99 为 4.93 ms，余量 3.4 倍。**

十万点档的附加测量：

| 指标 | 数值 |
|---|---|
| 1920×1080 整帧 | 6.650 / 7.245 / 7.740 ms（P99 仍远低于 16.7 ms） |
| 单帧点云内存 | 1.18 MB（3 个 float 数组） |
| 单帧报文字节 | 1.18 MB（每点 12 字节，未压缩） |
| 单次生成 | 0.485 ms，占 50 Hz 步进预算的 2.4% |

**结论 1：渲染不是瓶颈，且余量极大。** 十万点在 720p 下 P99 为 4.93 ms，是 60 FPS
预算（16.7 ms）的 30%；即使上到 1080p 也只占 46%。点云段本身只有 0.42 ms，即每百点
0.4 µs——这得益于直接写扫描线而不是逐点 `drawPoint`（后者在同机实测为 60~90 ms）。

**结论 2：整帧的大头不是点云，是画车。** 十万点档整帧 4.22 ms 里有 3.8 ms 花在
792 个圆角矩形的抗锯齿绘制上。真实场景只有几十辆车，这部分不到 0.3 ms；所以在
正常工况下整帧是 0.3~0.5 ms，比压测数字乐观一个量级。

### 3.2 感知（纯 Python，MAX_POINTS = 20000）

| 输入点数 | 抽稀 | 有效点数 | 簇数 | 单帧耗时（中位） | 占 20 ms 节拍 |
|---:|---|---:|---:|---:|---:|
| 3,120 | 不抽稀 | 3,120 | 24 | 9.0 ms | 45% |
| 18,720 | 不抽稀 | 18,720 | 24 | 60.5 ms | 302% |
| 49,920 | 1/3 | 16,640 | 24 | 34.8 ms | 174% |
| 99,840 | 1/5 | 19,968 | 24 | 38.7 ms | 193% |

**结论 3：感知侧才是瓶颈，而且不在"点数"而在"密度"。** 18,720 点比 49,920 点
（抽稀后 16,640）还慢，因为聚类成本约与"每格点数 × 总点数"成正比：抽稀同时降低了
两者，而单纯点多只是让链条更长。按实测斜率，纯 Python 感知的合理工作点是
**2~4 千点**（约 6~10 ms），当前 `MAX_POINTS = 20000` 是为"不丢目标"设的保守值，
代价是 35~39 ms/帧。

**结论 4：抽稀本身有精度代价。** 按索引等步长抽样会打散轮廓的连续性，框拟合的
长宽比在抽稀比 1/5 时出现 ±0.3 m 波动。这一项只测了耗时，精度影响需要单独实验，
列入后续工作。

### 3.3 端到端（十万点，真实双进程）

```
运行时长      : 16.0 s
状态帧/指令帧 : 801 / 801         ← 49.9 Hz，无丢帧
点云帧/点数   : 154 / 102,960     ← 9.6 Hz，一帧一点不差
感知单帧      : 9.11 ms（含 10 Hz 点云与 50 Hz 状态交替的摊薄，见说明）
决策分布      : {'cruise': 801}
协议异常      : 无（失步 0 / 丢片帧 0 / 坏包 0）
```

说明：9.11 ms 是"按状态帧平均"的结果。点云 10 Hz、状态 50 Hz，`Perception.process`
对同一帧点云只更新一次航迹（其余 4 次命中缓存），因此每点云帧的真实开销约
**38.7 ms**，被摊薄成 9.11 ms。这两个数字必须一起看：前者决定最坏情况下的指令
延迟，后者决定平均节拍。实测状态帧仍稳定在 49.9 Hz，说明 38.7 ms 的块状开销
被 TCP 缓冲吸收，没有把指令流拖垮。

GUI 侧同步读数（截图 `docs/images/stress_100k.png`）：102,960 点、光栅化 4.01 ms、
刷新 99.2 FPS、物理 50.0 Hz、帧 907 @ 18.14 s。

## 4 三个反直觉的结论

### 4.1 十万点不是真实交通的量级

自车 50 m 量程、每车轮廓 12.8 m：即便按 0.1 m 的高密度采样，一辆车也只有 130 点。
十万点意味着量程内要有 770 辆车——在 50 m 半径（7,850 m²）内每 10 m² 一辆车，
物理上不存在。

要凑到十万点只有两条路：把量程拉到 250 m 并铺满 24 条车道（本报告的做法），
或者把采样密度提到 40 点/米（3.3 cm 间距，只有近距离多线雷达才可能）。
**所以"十万点 ≥60 FPS"应当表述为"渲染与内存的上界测试"，而不是"常见工况"。**
真实车流（4 车道、150 m 量程、0.1 m 采样）的工作点约 2 万点，对应整帧 1.4 ms。

这一条必须写进论文：答辩时"你这个场景现实中有吗"是最容易被问到的问题，
主动说明比被追问好。

### 4.2 点云段只占整帧的十分之一

十万点看着吓人，但在 0.1 m/px 的缩放下视口只覆盖 128×72 m，约四成点落在视口外，
逐点只做了一次边界判断就被 `continue` 掉了。真正花时间的是对 792 个车身做抗锯齿
圆角矩形。**优化方向因此不是"更快地画点"，而是"少画车"**——真实场景已经自动满足。

### 4.3 分片尺寸不是越大越好

| 每片点数 | 片/帧 | 片大小 | 发送 中位/p95 | 是否超 MTU |
|---:|---:|---:|---:|---|
| 2,000 | 52 | 24,024 B | 2.550 / 3.149 ms | 是（约 17 个 IP 分片） |
| 120 | 858 | 1,464 B | 5.953 / 6.541 ms | 否 |

按 UDP 协议上限（65,507 B）切是够的，但按 MTU（1500 B）切才对：24 KB 的报文
在环回上能整包通过，一旦经真实网卡发出就会被 IP 层切碎，丢任一分片整包作废，
丢包率被放大十几倍，且接收端要等重组。代价是片数从 52 涨到 858、发送耗时
从 2.5 ms 涨到 6.0 ms（占 20 ms 节拍的 30%）。

这个代价在实时链路上偏高，说明"十万点走 UDP"本身就不是可持续方案：
**正确做法是发送前按体素或角度抽稀，而不是把原始点云硬塞进网络。**
当前实现取了正确性（不超 MTU），并把 858 片/帧的代价如实记在这里。

## 5 压测暴露的两个缺陷（已修）

压测的价值一半在数字，一半在它逼出来的 bug。这两个问题在 2 车 40 点的场景里
永远不会出现，一上十万点立刻致命。

### 5.1 点云按物理步 50 Hz 发布

`SimController::publish()` 原来每步都发点云。物理 50 Hz × 858 片/帧 = **4.3 万个
UDP 分片/秒、约 51 MB/s**，直接把链路灌死：算法进程 18 s 内只拼出 122 帧完整点云、
767 帧因分片交错而作废。

修法：`LidarParams` 增加 `rateHz`（默认 10），点云按传感器频率发布、状态仍按物理步
发布。用累加器而不是"每 5 步一次"，因为 50/10 恰好整除只是巧合，换成不整除的
组合取模会固定丢半拍。同时把快照改成懒重建（`snapshotDirty_`），点云与渲染各自
按需取样，避免十万点下每秒多做 40 次无用采样。

### 5.2 排空 UDP 把 TCP 饿死

算法进程主循环里 `_drain_udp()` 是"一直读到 EWOULDBLOCK"。十万点时接收缓冲里
几乎总有下一个分片在路上，于是这一轮事件循环永远轮不到 TCP——**18 s 内状态帧
0 个、指令 0 条**，表现是"点云收到了、车不动"。这个现象极难从表面反推原因。

修法：单次排空上限 320 片（约 1/3 帧），既摊销 `select` 开销，又保证每轮都给
TCP 留出机会。修复后同一场景 801/801 状态帧、零协议异常。

## 6 回归

改动触及发送节拍与快照缓存，四条既有基线全部重跑：

| 基线 | 结果 |
|---|---|
| `adasim_headless` | 1500 步闭环 + 回溯重推演逐位一致 `[PASS]` |
| `run.py --self-test` | 13/13 通过 |
| `standby_guard_check` | 10/10 `[PASS]`（含对照组 -4.46 m 追尾） |
| `following_lead` 端到端 20 s | 状态/指令 1001/1001、点云 200 帧（10.05 Hz）、最小车距 7.80 m、最小 TTC 2.87 s、协议异常 0 |

与改造前的差异（点云帧 1000 → 200、稳态车距 7.96 → 7.80 m）是预期内的：
感知从"每步都有新点云"变成"10 Hz 更新 + 中间帧靠预测"，跟踪器的更新频率降到
物理的 1/5。这更接近真实传感器，也让 5.1 的数字有意义。

## 7 结论与后续

1. **渲染层达标且余量大**：十万点 720p P99 4.93 ms、1080p P99 7.74 ms，相对 16.7 ms
   的验收线分别有 3.4 倍与 2.2 倍余量；上界测试到 40 万点（P99 5.96 ms）仍未破线。
2. **感知层不达标**：纯 Python 在 2 万点上是 35~39 ms，超 20 ms 节拍 2 倍。
   十万点只能靠抽稀"假装"达标，代价是精度损失。
3. **链路只能算勉强**：十万点 10 Hz 需要 858 片/帧、6.0 ms 发送时间、99 Mbit/s。
   实时可用，但已无余量。

后续三项，按性价比排序：

- **感知向量化**（最高优先）：numpy 把聚类与 PCA 搬到 C 层，预计 20 万点可进 5 ms，
  抽稀阈值随之可以取消。这是当前唯一真正卡住规模的环节。
- **发送前抽稀**：在底座侧做体素下采样（0.2 m 体素），十万点可压到 2~3 万点，
  链路开销降到 1/4，且不影响聚类精度（体素保形优于等步长抽样）。
- **点云压缩**：帧间增量或量化到 16 位，可再省一半带宽；优先级低于前两项。
